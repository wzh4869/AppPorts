# 按需阅读：语义自检（写完笔记后过一遍）

> 脚本管结构，这张清单管意思。写完后自检，只向用户报缺口和写得好的地方，不逐条背诵。
> 定位：这是给 Agent 的自检，不是给脚本的规则——下列检查点全部是语义判断，永不进 verify 脚本。

## 动手前：先自己查，再问用户

- [ ] 这个"问题"真的是决策吗？——能用 §3 检索四法（入口注释若有 / 分类树 / rg / 模块文档）自己查到的事实，不要抛给用户。Finding facts is your job; 只有取舍和拍板才占用用户时间。

## Problem

- [ ] 动机脱离方案也能独立成立——删掉 Decision 再读一遍，还是同一个问题吗？
- [ ] 触发清楚：什么破了、什么要变、不做会怎样。

## Decision / Proposal

- [ ] 具体到能行动，不是"用更好的数据库"而是"为会话存储用 SQLite"。
- [ ] 理由是被"vs"逼出来的——写"决定用 X"就补一句"X vs Y 为何选 X"。

## Alternatives considered

- [ ] ≥2 个真备选；不要编没权衡过的选项。「不做/复用」仅当当时真的考虑过才算一档，不是必填档。
- [ ] 每个被否项先写它最强的论据，再写为何否——只写弱处的拒绝是稻草人。
- [ ] 否掉的理由落到具体驱动条件，不是"经验上不行"。

## Consequences

- [ ] 代价和收益都写。自问"什么变难了？维护成本是什么？"——只有收益的后果是挑选过的。
- [ ] 简化注明已知上限与何时该重访。没有升级触发条件的简化会悄悄变永久。
- [ ] 没有基线就不写相对量词——"提升了/更快了"说不清基线时，降级为事实陈述。

## Verification / Testing（implemented）

- [ ] 落到可确认表面：哪条路径、什么量级、跑什么命令。
- [ ] 不写"看起来能用"——验收标准要么可勾选，要么明确留给后续。

## 汇报形态

写完自检后，这样汇报（一行一缺口，没缺口就收口）：

```markdown
**语义自检：<filename>**
✅ 稳定：动机独立成立 / 有 2 个真备选 / 后果代价收益兼备
⚠️ 缺口：
- Alternatives — 有"做了 vs 不做"稻草人，补一个与现行方案平行的真实选项
- Consequences — "性能提升"要落到哪条路径、什么量级
建议：修以上 2 处后落盘 / 可接受缺口，直接放行
```

用户接受缺口即放行；不接受就修再落盘。意思上的判断不是脚本，别把它撑成另一道检查。

## 这套自检生效了吗（观测判据）

每隔一段时间回看，以下信号说明自检在起作用；信号消失说明它在空转：

- 你向用户提的问题里，**不再出现**翻一下笔记树或 rg 一下就能答的事实性问题。
- 汇报里的每条缺口都带着**具体修法**（改哪节、补什么），而不是"建议再完善"。
- `rejected/` 和 Alternatives 里被否掉的路线，**不再被新会话重新提出**——这正是整套系统存在的理由。
