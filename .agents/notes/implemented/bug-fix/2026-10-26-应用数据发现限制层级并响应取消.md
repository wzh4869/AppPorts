# Agent Note: 应用数据发现限制层级并响应取消

Status: implemented

## Problem

应用数据候选搜索虽然在递归枚举结果中检查深度，枚举器仍可能在调用方判断前访问更深节点。为无关条目预取资源属性也扩大了读取范围；切换应用后，旧扫描若不响应取消，会继续占用扫描器并可能交付已无用的结果。

## Decision

`DataDirScanner.findMatchingDirs` 使用两轮 `contentsOfDirectory`，只列举搜索根下第一层和真实目录下第二层，跳过隐藏项且不预取资源属性。逐项用 `lstat` 检查条目本身，仅目录与软链参与名称匹配；软链可成为候选，但不作为下钻目录。第一层即使命中仍检查其第二层，第二层不再递归；FIFO 等特殊文件不作为目录候选。

读取诊断只记录搜索根、已匹配目录范围或名称匹配目录的失败，不把无关应用目录的访问限制计入所选应用。主扫描各阶段、候选循环、容器递归访问和目录列举检查 `Task.isCancelled`；顶层取消返回空结果，视图在交付结果前继续检查取消及扫描 token，取消不被呈现为成功确认没有数据。

两层限制属于名称候选发现，不改变普通 Containers 的精确 bundle ID 发现、容器内部展示树或迁移时完整数据验证的范围。

## Alternatives considered

以下依据 `191d101` 的前后实现比较。

- 递归枚举后按深度 `skipDescendants`：调用简单且可批量预取属性，但不能在枚举器访问节点之前约束读取，因此改为显式两层列举。
- 列举时预取目录和软链属性：省去调用方逐项查询，但会为无关特殊文件安排元数据读取，因此先用 `lstat` 检查条目类型。
- 仅在界面拒绝旧结果：能避免覆盖新选择，却不会终止底层继续发现，因此扫描器也设置取消检查。

## Consequences

候选搜索的访问层级可以直接从循环结构确认，取消也能在遍历阶段停止后续工作。代价是第三层及更深的名称候选不会发现；第一层目录非常多时仍有逐项元数据成本。取消是协作式检查，不能中断已经进入的同步文件系统调用，也没有由此证明网络卷上的固定响应时间。

## Verification

`DataDirScannerTests.testAppDataDiscoveryStopsAtTwoLevelsAndIgnoresSpecialFiles` 覆盖直接目录、厂商二级目录、三级排除与 FIFO；`testCancelledAppDataDiscoveryReturnsWithoutPublishingItems` 覆盖预先取消。两项均使用临时夹具。本次核对测试与源码，未重新执行；扫描中途取消及阻塞文件系统调用没有由这两项测试证明。
