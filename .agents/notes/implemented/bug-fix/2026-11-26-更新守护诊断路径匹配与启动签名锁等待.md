# Agent Note: 更新守护跳过诊断、路径规范匹配与启动签名维护锁等待

Status: implemented

## Problem

2026-11-24 的用户诊断包（AppPorts `2.3.1 (80)`）暴露出三项通用缺陷：

1. **更新守护静默跳过不可排查**：受管 Electron/ShipIt 应用在外盘本体丢失期间，后台更新守护进程持续运行但未输出任何日志；诊断摘要也不包含守护开关、就绪状态和监听数量，事后无法区分是未纳管、某条校验条件未命中还是旧版逻辑导致跳过。
2. **ShipIt 日志目标路径匹配脆弱**：`ShipItUpdateRecovery` 原本仅用 `attempt.contains(target.path) || attempt.contains(request.targetBundleURL.absoluteString)` 绑定失败日志与外盘目标。外盘卷名或应用名含中文或空格时，若 `ShipItState.plist` 与 `ShipIt_stderr.log` 中 `file://` URL 的尾部斜杠或 NFC/NFD 规范化不一致，两种子串匹配会同时失败；且无边界的子串匹配会让 `App.app` 误命中 `App.app.bak`。
3. **启动期签名自动收尾频繁误报全局锁占用**：同一诊断包在 11-20、11-22、11-24 三次打开 AppPorts 时，启动初始化并行执行 `BackgroundAgents.synchronize()`（持 `operation.lock` 同步 LaunchAgent）与 `OperationMaintenance.performMaintenance()`；其中的 `CodeSigner.performAutomaticMaintenance()` 直接调用非阻塞 `tryAcquire()`，瞬间触发 `OPERATION-GLOBAL-LOCK-BUSY` 并占据 `recent-failures.json` 的最近失败记录。

## Decision

1. **按需记录去重后的 ShipIt 跳过原因，并在诊断包加入纯聚合守护状态**：
   - `ShipItUpdateRecovery.scanCandidates()` 在保留原有接手边界的前提下，仅当受管记录对应的 `<bundleID>.ShipIt` 目录存在 `ShipItState.plist` 或 `ShipIt_stderr.log` 时产出 `SkipObservation`（含稳定英文 `Reason` 码与状态/日志的 mtime+size 指纹）；无 `.ShipIt` 缓存活动的普通受管应用不产出跳过记录，避免暴露无关应用或刷屏。
   - `ShipItRecoveryMonitor` 按 `bundle_id` 记忆最近一次已记录的 `SkipObservation`，仅在首次出现、原因变化或缓存指纹变化时写入一条 `[TRACE] 跳过 ShipIt 更新候选`；监听集合数量变化时仅记录汇总数量 `monitored_count`，不展开应用列表。
   - 在 `UpdateRecoveryAgentInstaller.swift` 中新增 `UpdateGuardianReporting`，仿照 `VolumeStateReporting` 汇总脱敏指标（`enabled`、`ready`、`monitored_count`、`receipt_count`、`pending_rollback_count`，不含应用名、路径或凭据），由 `AppLogger.buildDiagnosticPackage` 写入 `diagnostic-summary.txt` 与 `diagnostic-summary.json`。单元测试未注入隔离目录或探针时，默认跳过真实 `launchctl` 与宿主数据目录读取。
2. **统一规范化 ShipIt 日志目标绑定与回退路径核对**：
   - 新增 `ShipItUpdateRecovery.pathsMatch(_:_:)` 与 `attemptReferencesTarget(_:target:requestTargetURL:)`：原始路径按 NFC/NFD 变体配合路径分隔边界匹配（允许尾部 `/` 与包内子路径，拒绝 `App.app.bak` 等续接字符）；从日志提取 `file://` URL 经 `URL(string:)` 解码百分号编码与标准化后，再与目标路径及包内子路径前缀做规范分解等价比对；最后兜底比对去掉末尾 `/` 的请求 URL 边界。
   - `ShipItUpdateRollback` 的 `nativeTemporaryApplications` 收紧 `file://` 截断标点并在 `nativeTemporaryApplications` / `requireRollbackLocation` 统一复用 `pathsMatch`。
3. **后台签名自动收尾等待操作锁，保持交互操作即时失败语义**：
   - `CodeSigner.performAutomaticMaintenance(lockTimeout:)` 默认采用 `OperationLock.appWaitTimeout`（15 秒），通过 `acquireMaintenanceLocks(timeout:)` 在共享超时预算内依次等待 `operation.lock` 与 `signature-operation.lock`（后锁超时或失败时立即释放全局锁）；遇到写入准入拒绝或任务取消时沿用 `OperationLock.acquire` 立即退出，不空等。
   - 交互式手动签名、还原与备份清理路径继续调用非阻塞 `acquireLocks()`，维持原有即时错误反馈与单测契约。

## Alternatives considered

1. **在诊断包中直接打包受管应用的 `ShipItState.plist`、`ShipIt_stderr.log` 与 `app-search-records.json`**：信息最完整，可一次性查看第三方更新器原始现场；但会引入大体积第三方缓存日志并在默认导出中泄露完整已迁移应用清单与路径，违反既有诊断导出隐私边界。改用纯聚合守护状态与按需去重的 `TRACE` 跳过原因码。
2. **将 `CodeSigner.acquireLocks()` 统一改为等待 15 秒**：改动最少且前后台统一；但交互式手动签名或清理遇到锁占用时应立即提示，且既有 `SignatureBackupCleanupTests`、`CodeSignerTests` 依赖立刻抛出 `.signatureLockBusy`。因此只为后台 `performAutomaticMaintenance` 新增带超时预算的 `acquireMaintenanceLocks(timeout:)`。
3. **在 `OperationMaintenance.performMaintenance()` 中硬性等待 `AppLibraryAgentSync` 任务完成**：能避开主程序自身的启动代理同步；但无法处理开机或插盘时独立容器卷挂载代理短暂持有 `operation.lock` 的跨进程竞争。直接让后台签名维护与数据维护共用 `OperationLock.appWaitTimeout` 等待，同时覆盖进程内和跨进程瞬时占锁。

## Consequences

- **收益**：
  - 后续收到诊断包即可直接判断更新守护是否就绪、纳管数量及某次 ShipIt 活动被跳过的具体原因码，无需盲猜或第一时间要求用户翻查系统缓存目录。
  - 外盘卷名或应用名含中文、空格、NFC/NFD 差异或 `file://` URL 末尾斜杠差异时不再误漏合法 ShipIt 失败日志，同时避免前缀相似路径误匹配。
  - 消除启动时 `BackgroundAgents.synchronize()` 与 `CodeSigner.performAutomaticMaintenance()` 撞锁造成的假 `OPERATION-GLOBAL-LOCK-BUSY` 报错，持续占锁或写入准入拒绝仍会如实记录。
- **代价与边界**：
  - `ShipItRecoveryMonitor` 的跳过日志去重保存在进程内存中，守护重启后对仍存在 `.ShipIt` 日志的受管应用最多再记一次 `TRACE`；仍不自动采集第三方 `ShipIt_stderr.log` 原文，遇到 `unrecognized_error_marker` 等新型第三方输出时仍需向用户索取日志片段。
  - 若 `operation.lock` 被外部长任务持续占用，后台签名自动收尾最多延迟 15 秒后才记录超时失败。
