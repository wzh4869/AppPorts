# Agent Note: 外观切换使用 NSApplication 外观恢复跟随系统

Status: implemented

## Problem

在 macOS 上，`NSHostingView` 一旦应用过非空 `.preferredColorScheme(.dark)` 或 `.preferredColorScheme(.light)`，后续再传入 `.preferredColorScheme(nil)` 时虽然会将 `NSWindow.appearance` 置回 `nil`，但 `NSHostingView` 内部缓存的 SwiftUI `@Environment(\.colorScheme)` 不会清除。用户从深色切回自动（`"system"`）后，界面仍停留在深色外观（在系统处于深色时从浅色切回同理卡在浅色）。此外，`WindowGroup` 上的 `.preferredColorScheme` 只覆盖主窗口 SwiftUI 内容，不会作用于 `AboutWindowController`、诊断导出面板、权限引导浮窗及 `NSAlert` 等 AppKit 窗口和弹窗。

## Decision

`AppMoverApp`（`AppPorts/Appports.swift`）不对其根视图施加 `.preferredColorScheme(...)`，而是通过 `NSApplication.shared.appearance` 统一驱动整个应用的外观，`AppPorts/ContentView.swift` 与 `AppPorts/Appports.swift` 共用 `MainWindowAppearance.defaultsKey`（`"appAppearance"`）。

`MainWindowAppearance` 负责将存储值映射并同步到 AppKit：

- `nsAppearance(for:)` 将 `"light"` 映射为 `NSAppearance(named: .aqua)`，`"dark"` 映射为 `NSAppearance(named: .darkAqua)`，`"system"`、`nil` 及未知值统一映射为 `nil`。
- `apply(_:to:window:)` 仅在名称变化时更新目标 `NSApplication.appearance`，并在传入窗口存在非空 `window.appearance` 时将其清回 `nil`，确保窗口及其 `NSHostingView` 继承应用与系统的 `effectiveAppearance`。
- `AppDelegate.applicationWillFinishLaunching(_:)` 调用 `MainWindowAppearance.applyStoredAppearanceIfNeeded()` 在主窗口首帧显示前完成同步；`AppMoverApp.init()` 保持在 `ContainerMountAgentInstaller.isRunningAsAgent` 退出分支之前不触碰 `NSApplication.shared`。
- `MainWindowAppearance.WindowView` 在 `viewDidMoveToWindow()` 与 `updateNSView(_:context:)` 中实时同步用户切换，无需重建根视图树。
- `AppPortsTests` 以 `AppPorts.app` 作为 `TEST_HOST`，因此 `MainWindowAppearance.isRunningTests`（检查 `XCTestConfigurationFilePath`、`XCTestBundlePath` 与 `XCTestCase` 类）在测试宿主自动启动及默认 `WindowView()` 初始化时跳过外观写入，防止本机 `UserDefaults.standard` 影响其他测试；外观回归测试通过 `appliesAppearanceInTests: true` 显式启用同步。

关联决定见[就绪权限展示与默认窗口尺寸](../feature/2026-11-16-就绪权限展示与默认窗口尺寸.md)与[测试注入目录还必须隔离记录库和共享日志](../testing/2026-10-01-test-state-isolation.md)。

## Alternatives considered

- **保留 `.preferredColorScheme` 并用 `.id(appAppearance)` 重建根视图**：能让外观逻辑继续留在 SwiftUI 视图修饰符内、避免修改全局 `NSApplication.appearance`；但每次切换外观都会销毁 `ContentView` 及其子视图树，丢失当前扫描状态、列表选择和页面缓存，且仍无法让 `AboutWindowController`、浮窗与 `NSAlert` 跟随应用外观。
- **仅设置主窗口 `NSWindow.appearance`**：可把外观影响限制在主窗口并清回 `nil` 恢复系统外观；但 `AboutWindowController`、`DiagnosticExportDialog`、`PermissionGuidePanel` 与 `NSAlert` 独立于主窗口，用户在显式浅色或深色模式下会看到主窗口与次级窗口/弹窗外观不一致。
- **在 `XCTest` 宿主启动时无条件按 `UserDefaults.standard` 同步 `NSApp.appearance`**：实现最直接且少一组环境守卫；但 `AppPortsTests` 使用 `AppPorts.app` 作为 `TEST_HOST`，宿主偏好会泄漏到依赖系统外观或特定外观的渲染测试，因而要求自动同步跳过测试宿主、由外观测试显式开启并恢复 `NSApp.appearance`。

## Consequences

- **收益**：从 `"dark"` 或 `"light"` 切回 `"system"` 时，`NSApp.appearance` 立即归 `nil` 且 `window.appearance` 保持 `nil`，主窗口 `NSHostingView` 的 `@Environment(\.colorScheme)` 与次级窗口、Sheet、面板和弹窗统一恢复跟随系统外观；冷启动无首帧闪变，不破坏现有视图状态，沿用 `"appAppearance"` 配置且无本地化文案改动。
- **代价与已知上限**：应用内外观依赖进程级 `NSApplication.shared.appearance`，全局同一时间只能处于单一应用外观；所有经由 `MainWindowAppearance` 的自动同步依赖 `isRunningTests` 守卫以保持测试宿主隔离。若后续需要支持多窗口各自独立外观，或新增直接读取 `appAppearance` 的独立进程入口，需重访本决定。
