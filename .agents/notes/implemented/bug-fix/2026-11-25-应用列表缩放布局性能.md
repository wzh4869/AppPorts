# Agent Note: 应用列表缩放布局性能

Status: implemented

## Problem

主窗口连续缩放时，应用首页的两列 `List` 会持续触发 SwiftUI 和 AppKit 布局。当前每行发布一个锚点，列表容器通过 `GeometryReader` 读取锚点位置，并把计算出的尾部间距写回 `@State`。窗口尺寸每次变化都会重新计算该值，状态更新又让两列列表重新计算。

## Decision

`AppLibraryPane` 保留 `GeometryReader` 只用于判断窄栏名称行数，固定列表表头和底部操作区的尾部间距为现有默认值。逐行 `anchorPreference`、`backgroundPreferenceValue` 和尺寸变化后的状态回写已移除，缩放过程中不再通过列表行锚点回写布局状态。

## Alternatives considered

- **继续逐像素更新锚点间距**：能精确对齐滚动条和操作列，但会让窗口缩放持续触发列表状态更新，与当前采样中的主线程布局热点重合。
- **重写为 AppKit 表格**：可以更直接控制单元格布局和滚动，但改动范围会扩展到选择、菜单、状态徽章和现有 SwiftUI 交互，暂不作为本次实验方案。

## Consequences

Release 构建成功。相同的 10 秒窗口缩放采样中，`layoutIfNeeded` 采样从约 58 降至约 4，`NSDisplayCycleFlush` 采样从约 94 降至约 6。应用列表、表头和底部操作按钮在实验版中正常显示，窄栏名称断点仍保留。固定尾部间距放弃了对原生滚动条实际位置的逐帧测量，当前界面未观察到明显错位。

窗口回归测试 5 项全部通过。该采样依赖同一台机器和相同的 CUA 缩放操作，不等同于固定 FPS 测量。
