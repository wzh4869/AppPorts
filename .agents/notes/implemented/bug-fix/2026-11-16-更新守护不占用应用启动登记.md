# Agent Note: 更新守护不占用应用启动登记

Status: implemented

## Problem

安装 2.2.1（55）后，主程序退出而更新守护继续运行，普通 open /Applications/AppPorts.app 返回 Launch Services -600，无法重新打开主窗口。暂停更新守护后，同一安装版通过同一 open 命令正常打开。这是安装后的真实失败，不是由隔离测试推测的故障。

## Decision

--update-agent 入口不创建 NSApplication。它只保留原有 CFRunLoop、NSWorkspace 通知、DispatchSource 信号和 ShipIt 恢复器。NSApplication.shared 会把无窗口进程也登记为 AppPorts，导致 Launch Services 将后续打开请求交给后台进程；禁止激活不能消除应用登记。

Debug 观察只通过可选 NSApp 读取窗口与激活策略。独立子进程测试同时核验窗口数为零、没有激活策略，以及 NSRunningApplication(processIdentifier:) 查不到后台进程，避免只验证没有窗口而漏掉登记冲突。

本决定收窄[后台更新守护与主窗口设置](../feature/2026-11-16-后台更新守护与主窗口设置.md)的后台启动约束，保持开关、事件检查、操作锁、任务状态和更新恢复规则。第一次安装保留的旧包仅用于本轮可执行回退，最终验收后删除，不建立长期归档。

## Alternatives considered

- 要求所有打开命令使用 open -n：能强制创建实例，但用户从 Finder 或 Dock 正常打开仍会失败；修复后台登记原因才能恢复正常启动方式。
- 为守护建立独立应用包：可以区分身份，但增加签名、权限和更新安装路径；现有工作只需事件循环，移除 NSApplication 更直接。
- 保持 NSApplication 并设为 prohibited：能隐藏窗口与 Dock，但实机 -600 对照证明它仍占用应用登记。

## Verification

build 56 的 Debug build-for-testing 与 87 项后台、任务、ShipIt 和自更新专项执行成功：85 通过、2 项可选签名夹具跳过。build 57 最终专项 144 项通过、2 项可选签名夹具跳过，包含子进程无应用登记断言；最终截图夹具由两项设置渲染补跑覆盖。同证书 Release clean build 和严格签名核对通过。

build 57 已替换安装版并实机验证：正常退出本体并等待后，只有 PID 24647 的更新守护运行；普通 open /Applications/AppPorts.app 返回 0，GUI 以新 PID 31336 出现，守护 PID 未变。open 执行前已用进程快照确认没有 GUI，执行成功后才调用界面工具，避免工具自动重开掩盖失败。安装与过程证据在本地 build/Validation/settings-appstore-20261116/installation.json。

原故障及暂停守护后的对照保留在本地 build/Validation/background-agents-20261116/installation.json。两份临时旧安装包在最终核验身份、签名和无打开文件后删除。全量测试、真实后台应用更新及登录流程未验证；没有修改真实受管应用或系统权限来验证此修复。

build 58 仅追加 App Store 大小限制说明和构建号，更新守护源码与 build 57 一致。最终 16 项相关专项、同证书 Release 和安装核验通过；再次正常退出本体后 PID 41273 的守护持续运行，普通 open 返回 0，GUI 以 PID 42156 重开。最终安装证据在本地 build/Validation/settings-size-copy-20261116/installation.json，临时 build 57 包已核验并清除。

## Consequences

守护继续监听更新事件，主程序可由正常 Launch Services 路径启动。实现减少一次 AppKit 应用初始化；若未来后台加入依赖 NSApplication 的功能，必须保留独立登记约束并验证 GUI 退出后的普通重开。安全停止仍等待既有恢复释放操作锁。

最终同批源码已完成 build 61 的完整 runner 验证（保留当时批准延期的英文回退审计缺口）。全量结论以该轮为准，早期阶段的未运行声明只描述当时验证范围。
