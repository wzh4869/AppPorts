# Agent Note: 映像残留附件恢复与退出等待上限

Status: implemented

## Problem

映像附加成功后，设备信息读取可能超时或失败。下一轮虽然能识别该附件，但一律拒绝已有未挂载附件会让自动恢复永久停在此处。另一方面，代理配置同步会等待其他进程的操作锁，正常退出若直接等待其任务结束，可能无限保持待退出状态。

## Decision

已有未挂载附件允许按持久化的 APFS UUID 恢复：必须先核对映像路径及底层存储，再找到唯一匹配 UUID 的 APFS 卷，确认目标挂载路径空闲后直接挂载该设备。不再次附加，也不卸载已有附件。没有保存 UUID、UUID 不匹配或不能唯一识别的附件继续拒绝接管。新附加附件的失败清理规则保持有效。

本决定收窄[应用库映像后台自动挂载](../../implemented/feature/2026-11-03-应用库映像后台自动挂载.md)中“已有附件不接管”的范围。原限制避免对未知残留设备重复写入；现有路径、存储、UUID 核对足以支持挂载已知附件，无需再开一个写入附件。

退出配置同步最多等待 5 秒，以系统运行时长计时，独立于工作任务是否响应取消。超过期限返回退出拒绝，复用现有“还有任务尚未结束”和稍后重试提示，窗口继续可操作。配置任务继续运行，不取消可能已开始的配置写入；完成后用户可再次退出。更新退出同样遵守此边界，超时会取消更新安装的退出准备。真正的文件迁移和写命令仍沿用原来的安全收尾规则。

## Alternatives considered

- 一律拒绝残留附件最保守，但一次临时读取错误就会永久阻断后续自动恢复；仅对无法核对持久化身份的附件保留此限制。
- 先卸载残留附件再重新附加可复用新挂载路径，但会影响其他程序已附加的设备；核对后原地挂载无需卸载。
- 超时直接允许退出能立即关闭主程序，但代理配置可能尚未保存，无法兑现退出后的自动挂载；采用有期限的退出拒绝并给出重试反馈。

## Consequences

已知映像的临时设备信息读取失败可在下一轮恢复，UUID 未知的旧附件仍需人工检查。退出不会无限挂起，但其他进程长期占锁时用户仍需等待其结束后重试退出；本改动不强行中止那个进程，也不承诺尚未完成的配置已生效。

## Verification

隔离回归用例覆盖附加后读取失败再尝试只附加一次、已有不匹配附件不挂载不卸载、没有持久化 UUID 不接管，以及退出超时只回复一次且不停止配置任务。仅执行 Swift 静态语法与隔离依赖桩类型检查，以及笔记结构校验；未执行回归用例、应用构建或真实 NAS / USB 操作。
