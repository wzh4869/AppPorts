# Agent Note: 应用列表即时发布与手动大小重测

Status: implemented

> 迁移自 docs/superpowers/specs/2026-09-30-app-list-refresh-design.md
> 迁移自 docs/validation/app-list-refresh.md

## Problem

扫描会等待磁盘与签名探测，缺少进度时刷新看似无效。只比较应用根目录 mtime 的大小缓存，无法发现包内文件的原地增长；成功迁移若等待全量扫描才更新列表，也会继续显示过时位置。

后台维护写入 `UserDefaults` 会在写入线程同步发送变更通知。应用列表直接订阅该通知时，即使自定义扫描目录没有变化，SwiftUI 仍会在后台线程接收事件并报告发布警告。

## Decision

持久化展示缓存及目录汇总的扩展见[目录大小缓存仅用于展示](../feature/2026-10-21-目录大小缓存仅用于展示.md)，人工刷新强制重测的决定继续有效。

两侧列表分别用 `AppListScanState` 管理请求身份、进度和待重测需求。手动刷新强制重新测量大小；自动扫描复用有效缓存。自动请求接替手动请求时继承尚未完成的重测要求，旧请求不能发布结果或结束新请求。元数据不可读不构成缓存命中，本地入口大小与真实内容大小不混用。

首次使用或没有匹配清单时，本地和外盘在各自的扫描器中发现应用。首个已识别的应用立即发布，后续候选按约 150 ms 合并，完成目录时发出末批。预览与最终列表使用同一套去重和优先级，缓存命中时随行显示大小。每栏归并所有来源后独立发布正式列表，另一栏可以继续扫描。普通刷新保留该栏已有行。预览行只用于浏览，应用操作和应用数据页仍读取本轮已确认的列表。

从偏好设置恢复外盘时，路径变化负责发起首轮扫描。路径未变时由窗口出现负责发起。同轮两侧的元数据扫描可并行，缺失大小沿用四路上限；只有当前请求可以发布预览、正式结果或完成状态。

迁出、链接和还原成功后依据服务返回的实际源/目标更新两侧列表，保留身份与签名信息，同时失效旧扫描。操作完成协调一次后台扫描；失败项不发布成功。还原已生效而外部清理失败时保留外部副本行，不能因本地已可用就假装旧副本消失。

`ContentView` 的偏好变更发布者通过 `receive(on: RunLoop.main)` 向 SwiftUI 交付事件，再检查窗口可见性和自定义扫描目录变化。后台维护继续在原执行环境处理文件；通知交付到主线程时读取最新设置，保留多窗口目录同步行为。

应用大小缺失项的四路后台统计见[页面目录大小扫描优化](../architecture/2026-10-29-页面目录大小扫描优化.md)，请求身份、逐行发布和缓存边界继续适用。

## Related decisions

- 已有同来源清单时，先恢复上次的位置。后续决定与保留的逐批发现规则见[重开时恢复清单和排序](../feature/2026-11-22-首页重开恢复应用清单与排序.md)。

- 刷新按钮的当前页面分发、连接筛选及页面保留见[列表刷新筛选与页面状态保留](../feature/2026-10-26-列表刷新筛选与页面状态保留.md)，不改变本篇扫描请求与强制重测约束。

- 即时发布反映服务实际提交结果，持久化完成依据见[迁移以持久化切换和可重试清理为完成依据](../architecture/2026-10-10-verified-transfer-lifecycle.md)。
- 搜索实际展示与原入口验收不能由列表刷新测试代替，见[Spotlight 去重必须验收真实搜索与原入口](../testing/2026-10-09-spotlight-ui-acceptance.md)。

## Alternatives considered

- 持久保存整张首页能更早显示上次内容。逐行发现原先优先使用本轮识别的身份，以免混入旧外盘、旧链接和旧更新能力。后续清单通过卷身份匹配和只读预览解决重开时的顺序问题。
- 等待两栏都完成再替换能减少首屏排序变化。慢应用会让已经发现的行继续空白，因此只在空栏分批显示，同一来源的已有列表保留到复查完成。

- **始终复用根目录 mtime 缓存**：减少枚举，但来源已复现包内从 1,024 增至 8,192 字节而根目录时间不变。
- **每次自动扫描也全量重测**：可减少缓存陈旧，却增加常规监控的磁盘读取；明确的手动刷新承担强制重测。
- **操作后只等待完整扫描**：状态更新路径统一，却把已知的成功结果绑定到不相关的签名与大小等待。
- **将后台维护整体移到主线程**：可以避免其偏好写入从后台发送通知，但文件操作会占用界面线程，而且不能约束其他偏好写入来源；在界面订阅边界调度更直接。

## Consequences

用户能观察刷新进度，并立即看到已完成的位置切换。手动测量仍可能较慢，原有签名超时也可能发生；进度反馈不构成性能提升承诺。请求接替与旧版套件的部分清理结果需要额外状态回归。

偏好通知改为主运行循环调度，设置同步可能延后一轮事件循环；因此处理时读取最新值，不依赖通知到达次数。构建和逻辑测试不能代替启动、定时维护及多窗口同步的运行时检查。

## Verification

2026-11-22 的隔离 SwiftUI 窗口使用三个本地应用和一个外盘应用。测试在本地第一行完成后暂停后续识别：窗口已显示该行及命中的大小，外盘一行已完成并发布。放行后本地三行齐全。第二轮手动刷新暂停同一位置，原有三行保留，外盘独立完成。恢复保存的外盘时，启动日志只出现一次本地扫描和一次外盘扫描。专项回归 196 项 XCTest 与 43 项 Swift Testing 通过，覆盖候选去重、迟到批次、大小缓存及列表迁移。本次窗口夹具验证发布顺序，耗时取决于实际应用库。

`e19e409` 保留已实现行为。可检查 `AppPorts/Models/AppListScanState.swift`、`AppPortsTests/AppListRefreshTests.swift` 和 `AppPortsTests/AppListTransferTests.swift`。2026-09-30 来源记录最终 670 次执行通过，也保留了中间 codesign 超时；本次迁移没有重跑这些测试。

2026-10-15，build 32 通过应用列表刷新、大小重测、扫描请求、数据传输进度、后台维护进度、真实目录复制和旧重签任务停用的隔离回归：71 个测试，含参数化共 90 次执行，零失败。Xcode 实际调试启动后观察超过 15 分钟，后台维护多次执行；新增扫描目录能同步到另一窗口，未再出现后台线程发布警告。Release `xcodebuild clean build` 通过，异步 TaskLocal 弃用警告已消除；提高最低系统版本的工程建议保留，部署目标仍为 macOS 12.0。
