# Agent Note: 替换安装后自动清理并退场旧版更新守护

Status: implemented

## Problem

用户手动替换安装 `/Applications/AppPorts.app`（例如从 DMG/ZIP 拖入替换删除旧包，或将旧包移入备份目录后放入新包）不会触发应用内自更新的 `suspendForApplicationUpdate()`。常驻的 `com.shimoko.AppPorts.update-guardian`（`--update-agent`）进程继续留在内存中运行，但其内核可执行文件已处于两种异常态之一：

1. 旧包被删除/替换导致二进制被 unlink，`proc_pidpath(pid)` 返回空，但进程名仍是 `AppPorts`，触发 `WriterAdmission` 报错「运行实例的启动时间或可执行文件路径暂不可读」；
2. 旧包被移动到备份目录，`proc_pidpath(pid)` 变为备份路径，与 `.writer-presence/<pid>.plist` 记录的 `/Applications/AppPorts.app` 不一致，触发 `WriterAdmission` 写入兼容性拦截。

此时用户打开新版 AppPorts，启动阶段的 `BackgroundAgents.synchronize()` 本应通过 `launchctl bootout` + `bootstrap` 重建新版守护；但它默认获取带 `WriterAdmission` 检查的 `OperationLock()`，反而被它正准备停掉的旧 `--update-agent` 挡在锁外，形成死锁，导致后续全部应用与数据迁移被阻塞，直到用户手工杀掉该 PID。此外，若新旧 plist 字节一致（如无签名包）则 `configureAgent` 会命中 fast path 跳过重启；且 `--update-agent` 自身不会感知应用包被替换或挪走。

## Decision

界面判断接班是否完成时，读取[应用更新可用性与守护就绪判断](../feature/2026-11-21-应用更新可用性与守护就绪判断.md)定义的就绪快照。

采用两层防线同时解决「从任意旧版本替换升级」与「新版守护长期运行」两个场景：

1. **打破 LaunchAgent 同步的鸡生蛋死锁（`BackgroundAgentPreferences.swift`、`ContainerMountAgentInstaller.swift`、`UpdateRecoveryAgentInstaller.swift`、`WriterAdmission.swift`）**：
   - `BackgroundAgents.synchronize()` 与 `ContainerMountAgentInstaller.refreshAtLaunch()` 只变更 `LaunchAgents/*.plist` 和 `launchd` 注册，不写任何用户数据或迁移账本，改用仅 `flock` 互斥的 `OperationLock(writerAdmissionCheck: {})`；若旧守护正在执行恢复并持有 `operation.lock` 仍会等待，闲置时则直接持锁完成重启。
   - 新增 `WriterAdmission.isProcessCompliantWriter(pid:expectedExecutablePath:dataDirectory:)` 与 `ContainerMountAgentInstaller.runningServicePID(label:)` / `parseServicePID(from:)` / `waitForProcessExit(pid:timeout:)`。
   - `UpdateRecoveryAgentInstaller.synchronizeConfiguration` 核对当前运行中 `update-guardian` PID 的内核路径与 `.writer-presence` 能力登记；凡已失效或不合规（包含 plist 字节未变的无签名/同签名替换），传 `forceReload: true` 跳过 `configureAgent` fast path，执行 `bootout` 后有界等待旧 PID 退出（默认 3 秒），再写入定义并 `bootstrap` 新版代理。

2. **`--update-agent` 主动监听自身应用包与可执行文件变更（`UpdateRecoveryAgent.swift`）**：
   - 新增零轮询的 kqueue `ExecutableReplacementMonitor`，启动时记录自身可执行文件路径与 `(st_dev, st_ino)`，同时以 `O_EVTONLY` 监听可执行文件本身与所在 `.app` 目录的 `.delete` / `.rename` / `.revoke` 事件（避免移动整个 `.app` 目录时内层二进制无事件漏报）。
   - 事件触发并确认原路径文件身份变化或 `proc_pidpath(getpid())` 不再匹配初始路径时，走与 `SIGTERM` 相同的幂等优雅退出路径：`await monitor.stop()` 等待在途恢复释放 `operation.lock`，随后 `exit(0)`。因 plist 配置 `KeepAlive: ["SuccessfulExit": false]`，`exit(0)` 不会触发 `launchd` 拉起旧进程，待新版主程序打开时重新 `bootstrap`。

## Existing-note audit

- 与[后台更新守护与主窗口设置](../feature/2026-11-16-后台更新守护与主窗口设置.md)部分重叠并互链：保留「修改后台配置持有 `operation.lock` 不打断恢复」「`KeepAlive.SuccessfulExit=false`」的架构决定，补齐手动替换安装后同步不死锁与守护自检测退场边界。
- 与[后台写入者准入绑定实际进程与代理签名](2026-10-13-background-writer-identity.md)部分重叠并互链：维持所有实际数据写入仍严格执行 `WriterAdmission`（不放宽对不可读或路径失配进程的拦截），仅将只改 launchd 注册的同步流程与写入准入解耦，并复用其身份核对判断运行中守护是否陈旧。

## Alternatives considered

### 1. 在 `WriterAdmission` 中忽略 `proc_pidpath` 不可读或路径失配的 `--update-agent`

直接在 `WriterAdmission` 中放行此类旧守护可以避免迁移报错，但违背[后台写入者准入绑定实际进程与代理签名](2026-10-13-background-writer-identity.md)的核心不变量：内存里仍在运行的旧版守护依然可能使用旧写入约定去接手 ShipIt 恢复，与新版主程序并发冲突。正确做法是让旧守护退场并由新版重启，而不是放宽写入准入。

### 2. 仅靠 `--update-agent` 自己 kqueue 退场，不改 `BackgroundAgents.synchronize()`

只做 kqueue 自退场只对“未来再被替换的新版守护”有效；但已经装在用户机器上的旧版（如 2.3.0 build 75/77）没有这套自监听逻辑，用户升级到新版时仍会触发启动同步死锁并继续报错。因此必须同时打破 `BackgroundAgents.synchronize()` 的死锁并做陈旧 PID 强制重建。

## Consequences

- **收益**：
  - 用户从任意旧版手动替换安装到新版后，打开新版 AppPorts 即可自动 `bootout` 旧 `--update-agent`、等待其退出并拉起新版守护，无需手动查杀 PID；
  - 新版 `--update-agent` 在 `.app` 被移动或拖入替换的瞬间自动等待在途任务结束并 `exit(0)`，不再产生僵尸写入进程；
  - 正常数据迁移与恢复仍保持严格的 `WriterAdmission` 保护，未放宽任何并发写入安全边界。
- **代价与已知边界**：
  - `bootout` 后最多阻塞同步线程 3 秒等待旧 PID 退出；若旧守护因异常卡死超过 3 秒，后续首次迁移仍可能由 `WriterAdmission` 保守拦截并报错，不会静默绕过安全检查。
  - 若用户在旧包尚在后台运行且未打开新版时替换安装，且旧包来自本修复之前的版本，仍需打开一次新版主程序完成清理。
