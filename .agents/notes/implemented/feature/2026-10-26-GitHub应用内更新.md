# Agent Note: GitHub 应用内更新

Status: implemented

## Problem

浏览器下载后拖拽替换的更新流程要求用户重复处理下载隔离，且不能在应用内完成安装。现有 GitHub 最新发行版发布 AppPorts2.0.0.dmg，更新读取需要支持实际发布格式。

## Decision

GitHub 渠道从固定仓库 Releases API 的 assets 选择当前架构适用的 ZIP 或 DMG；下载地址限定 HTTPS 和 wzh4869/AppPorts 的发行路径，安装包必须具有有效的 GitHub SHA-256 digest。缺少 digest、附件不适用或选择存在歧义时保留发布页入口，不自动安装。Atom 兜底仍能提示版本，不能在缺少可信附件信息时自行拼装安装包链接。

GitHubUpdatePackage 在目标应用同卷的独占目录准备安装，先检查下载大小与散列，再只读挂载 DMG 或解压 ZIP。准备完成前校验 bundle ID、发行版本、最低系统版本、当前执行架构、可执行文件及已有签名完整性。允许项目目前的未签名构建，不接受已经存在但校验失败的签名。仅从验证后的候选应用移除下载隔离，不重新签名或修改系统 Gatekeeper 策略。签名身份变化仍可能影响系统隐私授权，约束沿用[微信挂载恢复事故](../bug-fix/2026-10-12-wechat-mount-recovery.md)。

下载状态由 AppUpdateController 跨窗口持有，取消或普通退出会等待准备清理。安装需要用户点击安装并重新启动，且取得 AppOperationState 的独占 token 和 OperationLock；仅该 token 是唯一操作时允许通过安装退出入口。后台 helper 等待旧 PID 退出后复核候选和目标目录身份，再保存旧版并替换应用；替换或启动请求失败时尝试恢复旧版。新进程通过独占目录内的 receipt 和启动 token 确认当前目标及版本，确认启动后 helper 才清理旧版备份。没有确认时保留新旧副本，不把 open 命令成功当成应用已启动。

国内官网提供网站下载。当前没有足够的受验证直链契约，不将官网页面当作安装附件。

## Alternatives considered

- Sparkle 提供成熟的更新及权限处理，但需要新增框架、受维护的 appcast 与发布签名配置；现阶段要求直接消费已有 Releases 附件，因此使用系统下载、散列、磁盘映像和文件工具，并收窄为可写安装位置。
- 下载后直接覆盖正在运行的应用实现较短，但会在旧进程仍使用旧资源、迁移任务仍存活时破坏应用本体，也缺少启动失败后的原件，因此使用退出后的 helper 和启动确认。

## Consequences

用户可从 GitHub 在应用内下载并安装更新；网站渠道保留浏览器操作。首次安装仍受系统安全检查约束；系统隐私权限不等同于下载隔离，不能保证跨签名身份继承。

安装目标必须是可写的真实应用目录，拒绝符号链接、只读卷和 /Volumes 下的路径，不提升管理员权限或更新本地 portal。无写入权限时提示手动更新。没有收到启动确认或清理失败时，隐藏的同卷 .AppPorts-update-UUID 目录保留旧版和日志，占用少量额外空间。需要管理员替换、更多附件布局或可靠发布签名时应重新评估 Sparkle。

测试使用临时目录的模拟应用，覆盖附件来源与架构筛选、digest 和大小、退出等待、文件身份变化、替换与确认清理、启动请求失败恢复和未确认时备份保留；不替换用户安装版，不对生产应用执行更新。真实 Gatekeeper、DMG 安装、重启和系统隐私授权仍需实际发行版本验收。

历史检索中，[设置中的关于与更新渠道](2026-10-26-设置中的关于与更新渠道.md)与本项部分重叠；后续[统一版本检查与更新方式选择](2026-10-26-统一版本检查与更新方式选择.md)调整版本检查与附件解析入口，本篇的安装校验、锁和恢复约束仍有效。签名授权事故提供独立约束，其余更新锁笔记涉及被迁移应用，与本次自身更新无关。
