# Agent Note: GitHub 应用内更新

Status: implemented

## Problem

浏览器下载后拖拽替换的更新流程要求用户重复处理下载隔离，且不能在应用内完成安装。现有 GitHub 最新发行版发布 AppPorts2.0.0.dmg，更新读取需要支持实际发布格式。

## Decision

GitHub 渠道从固定仓库 Releases API 的 assets 选择当前架构适用的 ZIP 或 DMG；下载地址限定 HTTPS 和 wzh4869/AppPorts 的发行路径，安装包必须具有有效的 GitHub SHA-256 digest。缺少 digest、附件不适用或选择存在歧义时保留发布页入口，不自动安装。Atom 兜底仍能提示版本，不能在缺少可信附件信息时自行拼装安装包链接。

GitHubUpdatePackage 在目标应用同卷的独占目录准备安装，先检查下载大小与散列，再只读挂载 DMG 或解压 ZIP。准备完成前校验 bundle ID、发行版本、最低系统版本、当前执行架构、可执行文件及已有签名完整性。允许项目目前的未签名构建，不接受已经存在但校验失败的签名。仅从验证后的候选应用移除下载隔离，不重新签名或修改系统 Gatekeeper 策略。签名身份变化仍可能影响系统隐私授权，约束沿用[微信挂载恢复事故](../bug-fix/2026-10-12-wechat-mount-recovery.md)。

下载状态由 AppUpdateController 跨窗口持有，取消或普通退出会等待准备清理。安装需要用户点击安装并重新启动，且取得 AppOperationState 的独占 token 和 OperationLock；仅该 token 是唯一操作时允许通过安装退出入口。后台 helper 等待旧 PID 退出后复核候选和目标目录身份，再保存旧版并替换应用；替换或启动请求失败时尝试恢复旧版。新进程通过独占目录内的 receipt 和启动 token 确认当前目标及版本，确认启动后 helper 才清理旧版备份。没有确认时保留新旧副本，不把 open 命令成功当成应用已启动。

`AppUpdateController` 将准备目录删除和等待 helper 退出串入后台清理任务，取消与普通退出等待下载任务及清理完成，安装退出也先等待已有清理，避免主线程同步删除或 `waitUntilExit` 阻塞。退出回调的存储与注入类型显式为 `@MainActor () async throws -> Void`；实际 AppKit 退出操作由主线程隔离的 `requestApplicationTermination` 执行。仅把控制器类标为 MainActor 不能保证未隔离异步默认回调的执行器，Swift 5 下该回调可能在通用执行器读取窗口和调用 terminate，造成界面持续显示退出中而 helper 等待旧 PID。安装退出先在主线程发布 `appPortsWillInstallUpdate`：ContentView 清除启动更新和设置弹窗的绑定，UpdateSettingsSection 清除嵌套更新绑定，共用 AppUpdatePresentationDismissal 接收事件。让出一次执行权后才由 AppKit 逐层完成 sheet 关闭；每个 sheet 只请求关闭一次，随后每 20 ms 异步检查分离状态，三秒未分离则报告退出受阻。helper 每 0.1 秒检查旧进程退出及启动确认，总等待预算不缩短。控制器观察当前 helper 的终止：应用仍存活而 helper 已退出时，取消退出任务、释放独占 token 并显示退出失败，保留准备包供重试；取消时移除 terminationHandler，已排队回调必须再次核对 helper 实例，不能影响后续安装。阶段日志记录清理完成、关闭弹窗、AppKit 退出请求和代理接收，区分任务悬挂与退出请求未完成。

国内安装来源由[国内应用内更新](2026-10-27-国内应用内更新.md)扩展：OpenList 按版本解析 DMG，使用官网 feed 散列验证，再复用本篇的包准备与安装约束；国内网站页面仍作为手动下载入口，不当作安装附件。

## Alternatives considered

- Sparkle 提供成熟的更新及权限处理，但需要新增框架、受维护的 appcast 与发布签名配置；现阶段要求直接消费已有 Releases 附件，因此使用系统下载、散列、磁盘映像和文件工具，并收窄为可写安装位置。
- 下载后直接覆盖正在运行的应用实现较短，但会在旧进程仍使用旧资源、迁移任务仍存活时破坏应用本体，也缺少启动失败后的原件，因此使用退出后的 helper 和启动确认。

- 仅用 AppKit endSheet 关闭窗口能兼容普通 NSWindow，却不会清除 SwiftUI 的显示绑定；真实 SwiftUI 用例在回调返回后仍保留 sheet，因此先通知呈现所有者清除绑定，再用 AppKit 完成残余动画。不把业务控制器绑定到某个具体设置窗口，也不依赖弹窗层数。

## Consequences

用户可从 GitHub 或国内站在应用内下载并安装更新；国内下载页面保留为失败后的手动入口。首次安装仍受系统安全检查约束；系统隐私权限不等同于下载隔离，不能保证跨签名身份继承。

安装目标必须是可写的真实应用目录，拒绝符号链接、只读卷和 /Volumes 下的路径，不提升管理员权限或更新本地 portal。无写入权限时提示手动更新。没有收到启动确认或清理失败时，隐藏的同卷 .AppPorts-update-UUID 目录保留旧版和日志，占用少量额外空间。需要管理员替换、更多附件布局或可靠发布签名时应重新评估 Sparkle。后台清理失败目前被忽略，不能承诺取消后不存在准备目录；关闭 sheet 的三秒截止也可能拒绝异常缓慢的界面退出。

自动化安装器测试使用临时目录的模拟应用，覆盖附件来源与架构筛选、digest 和大小、退出等待、文件身份变化、替换与确认清理、启动请求失败恢复和未确认时备份保留；不替换用户安装版，不对业务数据执行迁移。系统隐私权限继承仍需真实发布签名环境验收。

历史检索中，[设置中的关于与更新渠道](2026-10-26-设置中的关于与更新渠道.md)与本项部分重叠；后续[统一版本检查与更新方式选择](2026-10-26-统一版本检查与更新方式选择.md)调整版本检查与附件解析入口，本篇的安装校验、锁和恢复约束仍有效。签名授权事故提供独立约束，其余更新锁笔记涉及被迁移应用，与本次自身更新无关。

## Verification

AppUpdateTests 21 项与 UpdateCheckerTests 29 项合计 50 项通过，Release clean build（arm64 与 x86_64，禁用代码签名）通过。实测构建使用 MARKETING_VERSION=1.9.9 覆盖版本以触发 2.0.0 更新，仓库版本号不变。

真实 SwiftUI 回归在修正前复现：退出回调返回后 attachedSheet 仍存在，呈现绑定仍为 true；修正后启动单层和设置嵌套两种情况均通过。后台任务发起退出的测试确认，读取窗口、异步关闭 sheet 后检查模态状态以及调用退出都在主线程；模态窗口阻止退出的行为保留。helper 提前结束的测试确认安装状态与操作 token 被释放并显示错误。

GitHub 实机验收使用临时目录中的 1.9.9 应用副本，从启动弹窗选择 GitHub，完成真实发行附件下载、校验和准备。点击安装后，阶段日志确认历史清理完成、弹窗关闭完成、AppKit 退出及代理允许退出；旧进程结束，目标目录身份变化且版本成为 2.0.0，新进程从同一路径启动并展示主窗口，无需手动 xattr。实测副本随后正常退出；安装测试没有触发迁移或修改业务文件。

当前线上 2.0.0 包没有生成启动确认标记，所以这次验收确认实际退出、替换和启动，但不证明新版启动握手与自动备份清理；helper 保留旧副本及日志。模拟安装器测试另行覆盖启动确认后的清理。全量迁移测试未运行，原因是本项没有修改迁移、复制或恢复原语。

## Historical evidence boundary

原有记录对 f46d05a、aeb6334 和 c2951f0 的核对只涉及当时源码与测试定义，没有重跑那些历史版本。当前上述构建与 50 项测试是对本次实现执行的验证。原生窗口关闭测试不能代替 SwiftUI 呈现状态测试；阶段日志、主线程约束和真实呈现回归用于区分这两种表面相似的退出故障。

## Local testing signature and privacy permissions

禁用代码签名的构建仅用于编译及隔离测试，不能作为隐私权限实机测试包。向 /Applications 安装测试版时沿用项目已有 Apple Development 签名与开发团队，保持 com.shimoko.AppPorts 标识和默认 designated requirement；不为延续权限编造宽松 requirement，也不改变下载包原签名。

实机排查中，禁签测试包只有 linker ad-hoc 标识、Info.plist 未绑定且 bundle 严格校验失败；系统开关开启不证明该进程获准访问。使用项目自动签名重新构建后，双架构严格签名验证通过，designated requirement 与原 2.0.0 安装包完全一致。系统仍拒绝当前进程时，需要用户移除旧授权条目，重新添加当前 /Applications/AppPorts.app 并重启后再次实测；后续在完整签名测试版中复测，准备情况显示完全磁盘访问权限已就绪，当前进程已通过受保护文件读取检查。此处理只涉及本地交付包签名，没有修改权限探测逻辑或系统 TCC 数据库。
