# Agent Note: 外部应用库头部展示应用总大小

Status: implemented

## Problem

「外部应用库」面板头部仅展示 `%lld 个应用`（`AppPorts/ContentView.swift` 的 `externalAppsPane`），用户必须逐行心算或手动相加每行体积，才能了解外部应用库当前管理的应用占用了多少存储容量。

## Decision

`AppListDisplaySizeSummary`（`AppPorts/Models/AppModels.swift`）在界面展示层汇总外部应用列表的逻辑体积，不增加额外磁盘遍历，也不参与迁移准入判断：

- 按 `AppItem.id` 去重遍历当前展示列表（`filteredExternalApps`），累加 `size != nil` 条目的 `max(0, sizeBytes)`，并在任意条目 `size == nil` 时标记 `isCalculating = true`。
- `headerText` 按三态格式化：列表为空（`itemCount == 0`）返回 `nil`；尚未测出任何字节（`isCalculating && bytes == 0`）返回 `"计算中...".localized`；其余情况返回 `LocalizedByteCountFormatter.string(fromByteCount: bytes)`，若 `isCalculating` 为真则追加 `"（统计中）".localized`。
- `ContentView.HeaderView` 接收可选的 `sizeSummary: String? = nil` 参数，在副标题行 `appCount` 之后以 `·` 分隔展示（例如 `50 个应用 · 68.4 GB`），仅 `externalAppsPane` 传入该值；`Mac 本地应用` 与 `CustomDirsView` 保持 `sizeSummary == nil`。
- 数据来源直接复用 `AppSizeCacheStore` 缓存填充与四路并发增量扫描写回的 `externalApps` 条目，并复用意覆盖全语言的现有词条（`"计算中..."` 与 `"（统计中）"`），不改动 `AppPorts/Localizable.xcstrings`。

该展示值只反映外部应用包体的逻辑文件字节汇总，不宣称「已节省本机磁盘空间」。相关边界见[侧栏导航与存储空间展示](2026-10-29-侧栏导航与存储空间展示.md)、[大小缓存用于展示，执行判断重新读取事实](2026-10-21-目录大小缓存仅用于展示.md)与[页面目录大小复用原生遍历属性并限制应用统计并发](../architecture/2026-10-29-页面目录大小扫描优化.md)。

## Alternatives considered

- **始终统计未筛选的完整 `externalApps` 列表**：在搜索或切换「已链接 / 未链接」筛选时仍可看见全库总大小；但同一行紧邻其左的数字（`%lld 个应用`）统计的是当前筛选结果，口径分裂会让用户误解筛选后应用的总大小，因此与数量共用 `filteredExternalApps`。
- **标注为「已释放空间」或放进侧栏存储区**：能直接呼应用户对磁盘节省的关注；但外部应用包含未链接应用，且 APFS 克隆、系统可清理空间与硬链会导致逻辑字节不等同于本地实际回收容量，放入侧栏会重新引入已否决的「已节省」口径误导。
- **在头部额外执行一次外部目录总量遍历**：可以一次性得出整个外部目录大小；但会与 `AppScanner` 既有四路并发应用体积统计和 `AppSizeCacheStore` 缓存重复竞争磁盘 I/O，尤其是挂载在 SMB 磁盘映像或机械盘上的外部库。

## Consequences

- **收益**：用户可在「外部应用库」顶部一眼看到当前外部应用总数及对应总大小，缓存命中时随列表瞬时呈现，未缓存项在后台逐个测完时实时更新；筛选或搜索后数量与总大小同口径联动，未新增磁盘扫描或多语言缺译。
- **代价与已知上限**：`AppListDisplaySizeSummary` 汇总的是各应用包的逻辑文件字节数（受 `AppScanner` 单包 50 万文件上限约束），不等同于 APFS 物理块占用，也不代表本机已释放磁盘空间；外部应用包含未链接副本时，其体积同样计入当前可见列表汇总。若后续需要额外区分「已链接应用大小」与「全部外部应用大小」，需重访本决定与局部文案。
