# Agent Note: 统一版本检查与更新方式选择

Status: implemented

## Problem

版本检查渠道与安装方式绑定，启动检查依赖保存的渠道选择。GitHub 连接不稳定时，用户需要重新选择渠道才能获取版本说明，且无法在同一个更新窗口选择安装方式。

## Decision

启动和设置中的版本检查统一读取 `https://docs-appports.shimoko.com/latest.json`。请求跳过本地缓存，并采用三秒总截止时间；超时取消网络任务，手动检查显示失败，后台检查保持静默。显式 GitHub 检查接口仍保留供已有调用使用，界面不读取历史渠道偏好。

发现版本后，更新窗口展示该版本的本地化 Markdown 说明。底部提供 GitHub 应用内更新和原有国内下载页面。选择 GitHub 后，才向固定上游仓库查询弹窗所示 tag 的发行附件；版本必须匹配，附件必须通过既有来源、架构与 SHA-256 digest 筛选。下载、校验、安装确认、独占操作锁、退出替换与重启继续复用现有更新组件。

GitHub 附件信息查询使用三十秒截止时间，与三秒的版本发现请求分开，给 DNS 解析、连接与证书验证留出时间；附件下载沿用既有下载时限。网络超时、离线及安全连接失败映射为简短的用户提示，原始错误保留在日志。证书验证保持系统默认处理，收到其他域名的证书时拒绝请求。更新窗口底部左侧为关闭操作，右侧为两种更新方式；错误或下载、准备、安装状态统一由 `GitHubUpdateStatus` 展示在操作按钮上方；错误行截断并通过帮助文本展示完整内容，避免多处重复状态。

设置卡片使用图标、应用名、副标题和版本信息；设置视图保持固定宽度，卡片背景使用相同的可用宽度，滚动内容不展示滚动条。

发布说明继续由 `MarkdownTextView` 处理行级标题和列表，行内内容交给 Foundation `AttributedString(markdown:options:)` 的 `inlineOnlyPreservingWhitespace` 解析，再映射加粗、斜体、代码、删除线和链接到 AppKit 属性；解析失败回退原文。这样保留现有文本视图，同时避免手工按标记种类搜索时错过前方链接或代码的解析顺序问题，不承诺完整 CommonMark 块级支持。

## Alternatives considered

- 持久化检查渠道可以让用户自行绕开故障来源，但把版本检查和安装方式混在同一个选择中，因此统一发现版本，在新版本窗口选择更新方式。
- 选择 GitHub 后请求最新发行版实现更简单，但最新发行版可能已不同于弹窗展示的版本，因此按 tag 获取附件，并复核版本号。
- 仅使用 URLRequest 的超时参数可以限制无响应等待，但持续接收少量数据可能延长总耗时，因此增加可取消的三秒截止任务。

- 手工逐类搜索 Markdown 标记：无需引入解析转换层，但遇到混合行内标记时解析顺序依赖分支，`c2951f0` 改用系统行内解析并保留行级排版。该项依据提交前后源码对照补记。

## Consequences

版本发现只依赖文档站；该站不可用时不自动回退 GitHub。GitHub 不可达或缺少合格附件时保留错误和发布页入口，用户仍可选择国内下载。自动安装的安全检查和用户确认边界保持原有约束，不在测试中替换真实应用。

历史决策审计中，[设置中的关于与更新渠道](2026-10-26-设置中的关于与更新渠道.md)关于窗口复用的决定仍有效，渠道偏好与双源比较由本篇替代；[GitHub 应用内更新](2026-10-26-GitHub应用内更新.md)的校验、安装及恢复约束仍有效，本篇补充按版本解析附件的入口。其余 latest.json 相关记录涉及文档站部署或迁移锁机制，不与本项重叠。

定向验证范围为 UpdateCheckerTests：默认源隔离、新版说明、超时、指定版本附件及不合格附件拒绝。真实窗口布局和下载后的安装重启仍需实际发行版本确认。

## Retrospective verification scope

本次核对 `aeb6334` 与 `c2951f0` 的版本查询、状态呈现和 Markdown 变化，未重新执行应用测试。Markdown 仍有自定义块级规则，系统行内解析到 AppKit 的属性映射也需维护；目前没有独立的 Markdown 渲染回归测试，混合链接、加粗、代码及列表的实际展示仍需应用内确认。
