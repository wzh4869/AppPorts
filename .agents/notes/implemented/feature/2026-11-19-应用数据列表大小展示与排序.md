# Agent Note: 应用数据左侧列表展示大小与分组排序

Status: implemented

## Problem

「数据迁移 -> 应用数据」左侧应用列表原本仅展示应用名称与已迁移标识，用户无法直接比较各个应用的关联数据总体积，也无法快速分辨其中多少数据仍在本地、多少已迁移至外部磁盘；只能逐个点击应用等待右侧详情扫完才能估算。若对左侧全部本地应用逐一触发完整的单应用发现与高并发目录统计，则会按应用数线性放大 `~/Library` 目录树、外置镜像目录及挂载记录的重复枚举与磁盘竞争，在冷启动和大容器场景下拖慢页面响应。

## Decision

### 1. 口径统一拆分与置顶分组排序（`DataDirSpaceSummary.swift`、`DataDirScanner.swift`、`DataDirsView.swift`）

- `DataDirDisplaySizeSummary` 与 `DataDirScanner.deduplicateMeasurementRoots` 均使用 `!DataDirDisplaySizeSummary.isMigratedItem(item)` 判断子目录是否应由本地祖先吸收，使普通本地子目录不重复计入，同时保留挂载、受管软链、待接回及包含已迁移成员的微信部分拆分（`待完成`）子行；并通过 `isMigratedItem(_:)` 将总展示容量拆分为 `localBytes`、`migratedBytes` 与 `hasMigratedItems`（`bytes == localBytes + migratedBytes`）。对于处于 `待完成` 状态且存在本地祖先的微信拆分行，汇总阶段仅累加其已迁移成员的字节并跳过仍留在本地的成员，防止局部迁移时本地数据被本地容器祖先和拆分行双重计入。`isMigratedItem(_:)` 检查 `DataDirStatus.mountStatuses`、`linked`、`needsNormalization`、`pendingRelink`、`hasManagedLinkRecord` 以及递归检查 `weChatSplitMembers`；判断有意不包含裸 `hasMountTransferRecord`，避免已完成还原但尚未清理历史标记的本地目录被误算入已迁移项。
- `AppDataRowSizeSummary` 保存左侧单行的 `localBytes`、`migratedBytes`、`hasMigratedItems`、`isIncomplete` 与 `isCalculating`（`totalBytes == localBytes + migratedBytes`），仅供界面展示与排序，不参与迁移准入校验或旧副本清理决策。
- `AppListRow` 第一行右侧以等宽数字字体展示总大小（无字节且正在测量时显示 `"计算中...".localized`，若存在不完整读取则着橙色并显示警示图标）；当 `hasMigratedData || sizeSummary?.hasMigratedItems == true` 时，用次要文字在应用名下方显示「已迁移 · 本地」两项大小；macOS 13 及以上的窄栏按整项分行，macOS 12 使用文本换行。悬停提示与无障碍值同步两段数值。
- `AppDataAppListSorter`（由 `@AppStorage("appDataAppListSortMode")` 控制，默认 `.size`「按大小」，在搜索框旁菜单切换「按大小」「默认」「按首字母」）始终将 `migratedAppDataIDs` 命中或 `summaries[app.id]?.hasMigratedItems == true` 的已迁移应用置顶，未迁移应用置于其下，两组内部各自独立排序。`.size` 模式在每组内部采用三档桶位：已得出 `totalBytes > 0` 按字节降序 -> 测量中或尚无汇总项 -> 已确认 `0 B` 项，同级按 `displayName.localizedStandardCompare` 与 `id` 稳定排序。

### 2. 跨启动持久展示缓存、并发失效防污染与左右协同（`ToolDirectorySizeCacheStore.swift`、`DataDirScanner.swift`、`ContainerVolumeMigrator.swift`、`DataDirMover.swift`、`DataDirsView.swift`）

- `ToolDirectorySizeCacheStore.appDataDirectories` 在用户缓存目录（`Library/Caches/AppPorts/app-data-directory-sizes.json`）持久化版本为 `1` 的应用数据目录大小快照；应用数据缓存身份由 `AppDataSizeCachePolicy.cacheIdentity(for:)` 生成，除「源路径 + 解析目标路径 + 状态 + 设备号 + inode」五元组外，还附带后代 `ContainerMountRecord` 挂载态与 `ManagedDataLinkRecord` 构成的 `topologyFingerprint`，使子挂载启用、卸载或链接变化直接淘汰旧祖先大小条目。在 XCTest 环境中，`ToolDirectorySizeCacheStore.init(fileName:)` 自动重定向至 `temporaryDirectory/AppPortsTestCaches-<pid>/`，同时提供 `init(fileURL:)` 便于测试显式隔离路径。
- `AppDataSizeCachePolicy`（由 `DataDirScanResult` 与 `AppDataBatchPlan` 携带）同时基于 `ContainerMountStore.Inspection` 阻断瞬态副本污染：凡记录校验失败（`validationError != nil`）、存在尚未物理清理且未回滚的 `DataTransferRecord`（`retainedCopyRemovedAt == nil && rollbackCompletedAt == nil`）、待处理 `ContainerCleanupRecord`，或命中 `pausedMountDirectories`，与其源路径、激活路径、备份/暂存路径或挂载目标重叠的所有目录均返回 `isCacheable == false`，严禁读取或回写持久及内存大小缓存。
- 为防止后台扫描写回覆盖并发失效操作，`ToolDirectorySizeCacheStore` 维护队列保护的单调 `epoch` 并发守卫，暴露 `currentEpoch()`、`removeAll()`、`invalidate(for:)` 与 `merge(_:startedAtEpoch:)`（只合并清仓后且未在 `startedAtEpoch` 之后发生祖先/后代重叠失效的条目）；`MemoryDirectorySizeCache` 以同类 `NSLock` + `epoch` 机制过滤测量期间已失效的路径写回。
- `ContainerVolumeMigrator` 与 `DataDirMover` 在保留旧副本清理完成、`finishTransfer`（含 `retainedCopyRemovedAt != nil` 早退路径）、未切换暂存撤回以及 `performCleanup` 完成后均调用 `invalidateSizeCache(for:)` 联同清理原路径、备份与祖先目录的 RAM 及持久大小缓存；`DataDirsView` 在 `refreshTrigger` 人工刷新时同步清空内存缓存与 `ToolDirectorySizeCacheStore.appDataDirectories.removeAll()`，并在收到 `NSWorkspace.didMountNotification` / `didUnmountNotification` 时即时失效涉及卷的路径缓存——若当前处于 `operationState.isBusy` 迁移动作中，挂载事件仅记录 `deferredTabReloadAfterBusy` 而不在清理前抢跑重扫，待操作空闲后再执行 `reloadCurrentTab()`。
- 左侧批量统计与右侧详情 `DataDirsView.scanLibraryDirs(for:)` 共享 `ToolDirectorySizeCacheStore.appDataDirectories` 与内存 `MemoryDirectorySizeCache`（上限 `1000` 条）：右侧扫描在完成目录发现与微信账号分组后、发布 `discoveredSnapshot` 之前先填回经过 `sizeCachePolicy` 校验的持久缓存命中项，其余条目及微信拆分成员并行测完后写回 `weChatSplitMembers` 大小并以 `merge(_:startedAtEpoch:)` 回写合法条目；右侧扫描完成或命中 `AppDataScanCache` 内存快照时通过 `syncAppListSummary(from:)` 同步刷新 `appDataSizeSummaries[app.id]`，保证左右两栏一致。

### 3. 单遍索引、低优先级限流与全生命周期取消（`DataDirScanner.swift`、`DataDirsView.swift`）

- `DataDirScanner.buildAppDataBatchPlan(for:externalRootURL:)` 在单轮遍历内完成全部本地应用的测量规划：`ContainerMountStore.recordsForInspection()` 只读取一次；`~/Library/Containers` 执行单层 `lstat` 建立精确与小写映射，其余 9 类 `~/Library/*` 目录与外置盘对应镜像根各仅执行一次两层 `lstat` 索引；同一路径在同轮计划内通过 `inspectionCache` 去重状态检查，按 `deduplicateMeasurementRoots` 去重后按 `measurementKey` 合并跨应用共享测量目标到 `uniqueTargets`。容器根沿用 `FTS_PHYSICAL | FTS_XDEV` 的 `DirectorySizeTraversal` 单遍计入本地字节，天然跳过沙盒用户目录软链与内部挂载点，再将外置挂载与软链子目录单独归入 `migratedBytes`。
- `DataDirScanner.measureAppDataBatch(...)` 优先对 0 目标应用、且经 `sizeCachePolicy` 认定可缓存且命中内存 `MemoryDirectorySizeCache` 或持久缓存的条目生成首屏批次立即发布，并将缺失或不可缓存目标按「当前选中应用与已迁移应用优先」排入队列；实际测量运行在 `.utility` QoS 的 `withTaskGroup` 中且并发严格限制为 `2` 路，每 `250ms` 节流合并回调一次渐进汇总，并在批处理结束或因取消退出前通过 `merge(_:startedAtEpoch:)` 安全合并合法的已完成条目。
- 任何处于 `volumeMissing` / `waitingForUnlock` / `pendingMount` 状态的挂载条目或命中 `pausedMountDirectories` 的目录均标记 `isIncomplete = true` 并跳过磁盘遍历与缓存写入，确保离线或未解锁卷不产生虚假 `0 B` 缓存。
- `DataDirsView.scanAppListSizes(forceSizeRefresh:)` 仅在 `isActive && selectedTab == .appDirs` 时运行，且先检查 `LaunchReadinessChecker.fullDiskAccessState() == .granted`（权限未就绪时清空 `appDataSizeSummaries` 并立即退出，就绪面板关闭后自动重试）；离开「应用数据」标签、视图消失或 `operationState.isBusy` 触发时立即取消批量测量并在迁移空闲后恢复（`appListSizeNeedsResume`）；`localApps` 仅元数据变化而应用 `id` 集合与 `lastBatchSizedAppIDs` 一致时不触发整列表重扫；仅手动刷新或迁移记录变更时传入 `forceSizeRefresh: true` 绕过大小缓存重测。

## Alternatives considered

### 为什么不直接为左侧每个应用并发调用 `scanLibraryDirs`

该方案可以完全复用单应用发现逻辑，无需单独维护 `AppDataBatchPlan` 与索引结构。但左侧通常包含数十个本地应用，逐应用触发 `scanLibraryDirs` 会对相同的 10 类 `~/Library` 根目录及外置镜像重复枚举并重复加载 `ContainerMountStore` plist，且每次扫描按用户交互优先级分配 4 路并发遍历，会与用户当前选中的应用详情读取及外置磁盘 I/O 正面竞争。因此保留单应用路径服务右侧选中项与迁移预检，左侧全局汇总使用一次索引 + 共享目标去重 + `2` 路 `.utility` 限流。

### 为什么不直接读取 Spotlight 元数据（`kMDItemFSSize` / `MDQuery`）

Spotlight 属性查询开销极低，几乎无需磁盘目录遍历。但它对受保护的 `~/Library/Containers`、组容器、外置未完整建索引卷以及刚发生的迁移变更经常缺失或严重滞后，且无法按本地目录 vs 已链接/已挂载子目录拆出独立数值，也无法识别权限定向错误并标记 `isIncomplete`；同时单靠 Spotlight 会与右侧精确枚举得到的「应用数据」总量长期分裂，因此继续基于文件系统实测结合持久展示缓存实现。

### 为什么不按总大小直接混排全部应用，而要把已迁移应用置顶分组

纯总大小单列排序规则更少，磁盘占用最大应用必定出现在最上方。但在迁移工具的核心使用场景中，用户反复在已迁移应用上查看外置占比、切换挂载状态或发起还原；在未迁移大型应用较多时，体积较小的已迁移应用会被压到列表底部难以定位。因此把已迁移与未迁移固定分为上下两组、各自再按大小（或名称/默认顺序）排序，兼顾高频访问可达性与容量排查效率。

## Consequences

- **收益**：用户进入「应用数据」页面即可在左侧直接浏览总体积与已迁移/本地拆分，并以已迁移置顶 + 容量降序迅速定位大体积或已外置应用；二次访问命中 `ToolDirectorySizeCacheStore.appDataDirectories` 时可瞬时出数，冷启动阶段也仅对 `~/Library` 执行一轮两层 `lstat` 索引，并受 2 路 `.utility` 并发、250ms 批量刷新与自动让位迁移操作约束。
- **代价与已知边界**：展示缓存在原容器目录 inode 不变但内部嵌套文件增减时会保持旧值直到手动触发刷新；首次全冷启动在超大型容器目录下仍需后台读取目录树，左侧排序会在 250ms 批次完成时渐进稳定；当 `~/Library` 下存在超过两层的厂商嵌套数据目录时，列表汇总与单应用发现同样不会触及第三层独立名称匹配。若后续发现冷启动磁盘访问仍影响机械盘体验，可考虑为列表统计增加用户可开关的后台扫描选项或按目录修改时间追加增量重测。
