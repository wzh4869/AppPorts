# Agent Note: 首页重开时恢复两栏清单和排序

Status: implemented

## Problem

重新打开 AppPorts 时，两栏原有大小缓存只能在扫描认出应用后填入数值。新行按批次插到表格中，即使磁盘上没有变化，用户仍要等待目标应用出现，重新寻找它的位置。每栏的名称或大小排序也随窗口销毁而重置。

## Decision

本地与外部应用栏分别在本栏完成目录发现时保存清单。清单保留路径、名称、图标所需的内部应用路径、文件夹展示信息和上次链接状态。按应用路径从原有大小缓存取回数值，并区分本地入口大小和包大小。每栏独立保存排序列与方向，缓存预览和当前扫描共用一个比较器。

恢复清单时核对本栏的目录路径和各目录的卷 UUID。身份不全、来源变化、清单缺失或无法解码时，页面从当前扫描逐批显示。首次恢复的行只进入预览集合。到达的扫描批次替换相同路径并加入新行，尚未发现的旧行保留到该栏完成发现。迁移、链接与应用数据页读取本轮正式列表。持久化按栏串行原子写入，内容相同的清单跳过重写。

清单按行保存上次显示的更新、迁移、类型及签名徽章。恢复时与应用名称一起绘制，只读徽章与正式徽章共用文案、图标、颜色和胶囊布局。在行可操作之前，以静态标签显示并提供辅助功能名称。较早清单缺少徽章字段时，只按已知信息预留空间。本轮核对成功后，更新、锁定和类型徽章采用当前判断；运行和签名随实际目录扫描结果替换。任务状态始终取当前任务中心的数据。

首页清单另外保存真实包的更新组件识别结果，包括未知结果。重开时在后台核对真实包路径、所在设备、文件编号、应用标识、版本和构建号。匹配的预览行随即采用本轮的更新判断，守护就绪、文件锁、商店目标及旧版 Tauri 的当前入口仍实时判断。缺少版本与构建号、重装替换包、路径或身份改变的应用由当前扫描重新识别。更新识别规则改变时递增缓存规则版本。守护就绪或商店设置在目录发现结束后变化时，更新已确认清单中的徽章快照，供下次首屏使用。手动刷新跳过历史组件识别结果。以前的清单仍可恢复应用和排序，首次扫描补齐新字段。

## Alternatives considered

- 等到本轮锁和身份核对完成再展示徽章，可避免短暂显示旧值，但首帧只有名称和大小。按上次实际画面恢复只读徽章，允许外部条件变化时短暂显示上次结果，后到的真实结果逐行替换。持久化的可用性提示仅用于显示。

- 固定预留一行能容纳单个更新徽章。窄栏中更新、链接和运行徽章会换行；一律预留两行又会给普通应用和无徽章文件夹留下空白。保存排版所需内容可以随窗口和语言重新换行，无需记录每一行的像素高度。
- 从大小缓存的路径重建列表可以沿用原有文件，但其中也有过去测过的路径，还缺少单应用容器的展示名称、目录来源和所属栏。
- 完整持久化可执行操作的应用模型可以复用全部徽章，代价是用上次打开时的更新、运行或签名信息描述当前应用。保存显示字段并与当次结果按路径合并，现有的操作入口可以继续使用本次发现的对象。
- 仅使用扫描器逐批上报可以实时反映目录内容，首次使用和来源改变时沿用此方式；已知应用在每次重启时重新插入，会打乱用户查找顺序。

## Consequences

重开时可以直接浏览上次完成扫描的清单。退出期间被移除的应用会短暂出现，等该栏发现完成后消失。首次升级需要完成一次扫描来生成清单。重开多了一次按来源目录查询卷身份和两份小清单的读取，后台继续执行原有扫描。两次扫描之间实际徽章组合发生变化时，确认结果仍可调整行高。
