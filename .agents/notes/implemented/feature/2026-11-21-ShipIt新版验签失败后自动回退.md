# Agent Note: ShipIt 新版验签失败后自动回退

Status: implemented

## Problem

守护对所有接手失败沿用相同的五秒重试。下载包签名已经损坏、或不满足原开发者身份时，重复检查同一份包无法修复它。旧版可能仍在外盘，也可能被 ShipIt 移到了临时位置。让用户自行寻找副本会留下无法打开的入口和无用的下载。

## Decision

AppPorts 仅对同一请求、同一下载包文件身份连续两次明确的签名拒绝尝试自动回退。复制到外盘的中间包校验失败、I/O 错误、占用等仍走原有重试。只有原路径、安装收据或同一轮移动记录能定位签名有效且版本较低的旧包，才在现有回退记录写入可选的被拒包身份。旧记录沿用手动回退语义。

守护等应用和安装器空闲，重新核验下载和旧包，用原有操作锁、启动保护、回退及入口刷新流程恢复。旧包仍在原位时沿用原文件。准备恢复期间若下载已经修复，退出尚未产生复制操作的自动回退，允许新包重新校验。后台进程重启后可以继续已登记的自动回退。任务中心在恢复及清理均完成后显示「已回退」和版本。

自动清理按请求字节、路径和文件身份核对，删除本次被拒的应用包、其安装状态及能由收据确认的副本，只移除已清空的本次下载或临时目录。同目录的其他下载、共享日志及用户数据保留。没有可核验旧版时，任务中心说明原因，保留现有材料并等待相关事件。

## Existing note audit

[任务状态与干净回退](2026-11-15-ShipIt任务状态与干净回退.md)保留手动回退与历史兼容，本篇扩展为明确签名失败时的自动回退。[事件触发检查](2026-11-15-ShipIt事件触发检查.md)继续负责正常唤醒与调度。proposed 与 rejected 中没有相同职责的提案。

## Alternatives considered

- 遇到任何异常立即回退。暂时占用、缺盘或复制中断后仍可能成功安装新版。
- 自动删除整个应用的更新缓存。ShipIt 的缓存目录可以同时存放另一笔下载，自动回退只清理当前请求可确认的材料。
- 仅按名称或标识接受新版。覆盖已有应用前仍需满足旧版的签名身份要求。

## Consequences

签名失败的自动处置需要一次复查，旧应用运行期间会等待其正常退出。无法核验旧版时不会报告已回退。已进入写入阶段后现场改变，需要保留剩余材料以免误删新请求。

## Verification

回归覆盖同一包两次验签失败、原位修复的下载、无旧版、开发者不符、重启与保持旧版原位。外盘集成测试使用 DeepSeek 的签名旧包和被刻意损坏资源的新版副本，执行真实签名核验、恢复、入口刷新与定向清理。

本机物理外盘上，守护找回 ShipIt 移走的 0.2.2-rc.3，恢复至原外盘路径。本机入口重新指向该版本，任务中心只有一条回退记录。损坏的 rc.5 下载和本次安装状态已清除，相邻下载保留。九组专项共 188 项通过，零失败、零跳过。本地结果为 `build/Validation/guardian-auto-CZzNAzk8/Final.xcresult`。测试使用独立目录与后台监听，未替换已安装应用或运行全量套件。
