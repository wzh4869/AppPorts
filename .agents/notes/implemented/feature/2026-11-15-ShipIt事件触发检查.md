# Agent Note: ShipIt 更新恢复由文件事件触发

Status: implemented

## Problem

ShipItRecoveryMonitor 空闲时仍每五秒遍历所有迁移记录，逐项读取入口、外盘身份和更新状态。当前 64 条记录中有 43 条符合前置条件；闲置 15 秒整个 AppPorts 使用约 0.09 秒 CPU，不能把总开销全部归因于更新监控，但没有更新时的重复读取可以省去。

Pearcleaner 5.4.3 的 [Sentinel](https://github.com/alienator88/Pearcleaner/blob/5.4.3/PearcleanerSentinel/main.swift)用 FSEvents 监听废纸篓，变化时打开主程序。AppPorts 的 FolderMonitor 只监控目录这一层，无法单独捕捉已存在 ShipIt 日志的追加写入。

## Decision

本篇只在主进程运行的范围由[后台更新守护与主窗口设置](2026-11-16-后台更新守护与主窗口设置.md)扩展：同一安装版的无窗口代理执行自动检查，主程序观察任务结果；缓存过滤、合并、候选恢复和五秒待办重试原则继续适用。下面保留事件调度首次采用时的理由与验证，新增代理的配置、停止和验证缺口见扩展记录。

AppPorts 主进程使用一个 FSEvents 流监听用户缓存目录，回调仅接受受管 Bundle ID 对应 .ShipIt 目录本身、ShipItState.plist 和 ShipIt_stderr.log 的事件。缓存目录与附加监听文件在初始化时沿最近已存在祖先目录解析 `realpath` 并拼回尚未创建的末级文件名，保证首次创建账本或任务状态文件时仍能命中精确路径匹配。忽略其他缓存和解压文件，合并连续事件后调用现有候选检查及恢复逻辑。目录不存在或被删除重建仍由父缓存目录的事件捕获，不为每个应用开启描述符。

开始监听后进行首次检查；监听工作记录变化、应用退出、系统唤醒和外盘挂卸载通知进行补查。没有候选更新时不设置周期计时器；已有候选被更新器、应用或操作锁阻挡，或恢复抛错时，仅为未完成恢复安排五秒重试，完成或候选失效后停止。自身恢复收尾产生的记录通知不触发立即重试循环。

事件只决定检查时机，失败识别、版本和签名核验、启动保护、原子交换、备份及完成收据保持原实现。监听停止时取消计划检查和在途恢复，等待其释放操作 token。原有可选测试夹具和运行入口继续适用。

## Alternatives considered

- 保留五秒轮询并提前判断状态文件：改动小，能减少入口和外盘读取，但空闲时仍持续醒来；用户选择事件触发。
- 直接复用 FolderMonitor：已有实现，但不递归，日志追加不改变父目录条目；还需逐文件监听及删除重建管理。
- 新增 Sentinel 登录进程：主程序退出后仍可收到事件，但改变现有运行边界和安装注册流程；本次只替换主进程调度。

## Consequences

空闲时不再每五秒遍历迁移记录，状态和日志变化后才检查；恢复相关事件仍由原服务核验，不把系统通知当作失败证明。默认 FSEvents 延迟与调度合并窗口各一秒，事件触发不承诺零延迟。未完成恢复才使用五秒重试。生产 CPU 节省没有在安装版中单独量化；专项证明没有空闲周期扫描。

代价是新增一个 FSEvents 流和事件调度生命周期；缓存父目录仍会收到无关事件，先按路径筛选，不为它们读取迁移记录。开始监听及启动补查处理已有现场，唤醒、挂卸载和记录更新时补查；事件流启动失败的自动退避与界面就绪判断见[应用更新可用性与守护就绪判断](2026-11-21-应用更新可用性与守护就绪判断.md)。全局主进程退出期间仍不接手，不新增登录代理。只有出现更新但仍有有效失败候选时才持续重试，不代表消除实际恢复时的开销。
