# Agent Note: 应用更新可用性与守护就绪判断

Status: implemented

## Problem

用户需要知道迁移后可以在哪里更新，以及选择非锁定迁移是否合适。Electron 应用可以搭配不同更新器。AppPorts 升级以后，旧守护退出与新守护开始监听之间也有时间差。根据框架名称、用户开关或 launchd 注册成功推断可用，都会让界面过早给出推荐。

## Decision

扫描真实应用包，分别记录更新路径和当前文件锁。列表与确认弹窗共用更新能力判断。已验证由厂商组件独立完成安装并冷启动外盘新版的应用，按应用标识和包内可执行安装器识别，关闭守护或等待守护时都可用。其余仅识别框架或确认过守护接手的 Sparkle 和 Squirrel/ShipIt 仍依赖当前守护就绪。商店更新以真实收据和已配置的原生外盘目录为依据。网易云、WorkBuddy 和 DeepSeek 按标识登记已知框架路径。独立更新登记同时匹配真实应用标识和该包内预期的可执行程序，商店收据优先，其次匹配已验证的安装程序，最后才按框架回退。发现本机新版时显示“待迁出”。单次版本差异无法区分厂商更新和重新下载安装。

本机与外部列表都在应用名下方显示一组彩色徽章。适用时，更新状态排在这组徽章的首位，其后才是任务、迁移和运行等状态。

可点击的徽章同时支持悬停。指针停留 250 毫秒后，说明徽章展示点击时同一份本地化说明，任务与签名徽章打开原有详情面板。快速划过或列表行消失时取消待触发的动作。指针可以从徽章移进说明阅读，离开两处后关闭悬停预览；直接点击打开的说明沿用原有关闭方式。

只有批次中需要选模式的应用都可用，非锁定迁移才获得推荐和回车默认值。弹窗读取参与选择的实际包锁，已锁定或锁状态无法读取时保留手动选择。网易云与 WorkBuddy 沿用普通迁移。锁定、待迁出和孤立入口保留自己的操作说明。

更新守护读到受管应用清单、成功启动 FSEvents 后，才向原数据目录原子写入一次就绪快照。清单暂时读不出、事件流启动失败或快照写入失败时，从一秒开始加倍延迟，最长三十秒后重试。正常运行时只更新事件过滤名单，停止守护会取消待执行的重试。主程序同步后验证 launchd 服务 PID、进程身份、写入登记、构建号及可执行文件身份，统一向列表和弹窗发布结果。设置变化或已确认的守护退出会使结果失效。同步时发现守护定义相同且已注册、当前却没有 PID，则用不带 -k 的 kickstart 启动该服务。守护关闭时遵从原有偏好。此快照仅用于界面判断，写入准入与恢复收据继续使用原有格式。

[非锁定迁移默认选择与普通更新应用](2026-11-16-非锁定迁移默认选择与普通更新应用.md)中的固定默认选项由本判断取代，普通迁移例外继续生效。[替换安装后自动清理并退场旧版更新守护](../bug-fix/2026-11-20-替换安装后自动清理并退场旧版更新守护.md)继续负责旧进程退场和操作锁，本篇补充就绪证明。现有 proposed 和 rejected 笔记中没有同职责方案。

已实测的七款 Sparkle 应用按各自发行包内的 1.x 或 2.x Autoupdate 可执行文件匹配。Qoder 与 OpenCode 的原生 ShipIt 日志记载安装成功，原入口冷启动到了外盘新版，这两款在守护开启且就绪时仍提示额外的接手能力。GitHub Desktop 与 DeepSeek Harness 的失败样本需要守护接手。WorkBuddy 的迁移确认单独保留。各框架目录、应用名字和 Electron 运行时本身不能证明独立安装。

## Alternatives considered

- 仅检查更新守护开关或 launchd 服务存在。两者都可在旧守护尚未退场或新守护尚未监听时成立。
- 使用签名或版本号作为唯一身份。相同版本号下允许重新构建；以进程启动身份和已安装可执行文件的设备及 inode 进行核对，同时支持未签名构建。
- 逐行查询后台服务。不同应用行会重复查询同一个进程。后台同步统一核对后，还能让已打开的迁移弹窗同时收到变化。

## Consequences

“可用”说明已有更新方式。Sparkle 使用应用自身的更新能力，只有适配的 ShipIt 失败才由守护尝试恢复。未确认的应用仍可手动尝试。新增独立更新规则需要观察新版实际位置和原入口冷启动。仅有框架识别或守护恢复证据的 Sparkle、ShipIt 应用在等待就绪时显示「检测中」，关闭守护或未确认更新方式时显示「未知」。主程序等待就绪期间按退避延迟复核，最长间隔十五秒。设置显示正在重试，保留手动重试入口。确认就绪后即停止轮询，改为监听守护进程退出，即使启动耗时超过原来的十二秒，徽章也会自动刷新。

## Verification

- 在独立 macOS 窗口中加载实际徽章组件，用鼠标移动和按钮激活核对说明内容、快速划过、移入说明、移出关闭，以及任务和签名回调。另核对点击发生在悬停门限前时只触发一次，列表行消失会取消等待。6 项渲染测试和 19 项本地化审计通过。悬停复用同一个字符串键，主应用目录的 1,358 条文案在 22 种支持语言中都有翻译。

监听就绪改动在本机通过 117 项专项，零失败、零跳过。强制第一次启动事件流返回失败，守护未发布就绪；自动重试启动真实 FSEvents 后仅发布一次，并处理了随后写入的 ShipIt 失败日志。另一项测试在退避期间停止守护，确认没有第二次启动。独立的真实守护子进程在迁移清单不可读超过十二秒时保持未就绪，修复清单后同一进程恢复监听。测试向界面观察器传入该子进程的 PID，核验真实就绪快照、自动刷新和退出后失效，生产 launchd 注册未参与本轮故障注入。外盘另用原签名 DeepSeek 新旧副本验证接手及回退。完整结果在本地 `build/Validation/guardian-listener-llyticbc/Validated.xcresult`。

扫描、批量确认和渲染测试覆盖守护开关、真实文件锁、App Store 目录及混合选择。后台代理测试启动独立守护子进程核对其登记，终止后旧快照失效。守护就绪规则最初在 2.3.1（81）验证，2.3.1（82）增加按已验证原生安装组件区分的规则。

299 项专项通过，0 失败、0 跳过，包含真实签名应用包、锁定文件、确认弹窗的文档链接及 22 种语言审计。双架构 Release 洁净构建和解包后严格签名校验通过。弹窗复用统一文档链接组件，直达三语博客的迁移选择章节。

在独立的 macOS 15.7.7 环境中，原装 build 80 手动替换为 81 后旧守护退出，新守护自动发布就绪记录。另一条路径用旧源码 build 80 的测试入口将已准备好的候选包传给原有应用内安装流程，保持正式更新源和版本比较原样。验证了关闭偏好跨升级保留、安装器因另一主程序实例拒绝安装后恢复守护，以及已注册且干净退出的 build 81 守护在重新打开主程序后恢复运行。

升级后自动启动的 81 守护成功处理重放的 64 MiB 以上 ShipIt 日志，将原签名 DeepSeek Harness 从 0.2.1-rc.2 更新到外盘 0.2.2-rc.5。原入口冷启动和唯一的任务中心成功记录均已核实。另一次真实恢复在复制新版时尝试升级 AppPorts，被共享锁拒绝；当前守护完成该笔恢复后重试，才完成 build 80 到 81 的交接。

关闭守护，在 macOS 15.7.7 隔离机非锁定迁至另一 APFS 卷。DMG Canvas 4.2.2 → 4.2.3、Querious 4.2.4 → 4.2.5、Screenflick 3.3.2 → 3.3.3 使用 AraeliumUpdate，Firefox 160.0 → 160.0.1、Thunderbird 159.0 → 160.0 使用 Mozilla 更新器。Google Chrome 153.0.8010.48 → 158.0.8127.37、JetBrains Toolbox 3.5.0.84344 → 3.9.1.89198 和 Zed 1.29.2 → 1.29.3 也更新了外盘副本。八项均退出后经原本机入口启动，核对新版进程、外盘路径和厂商签名。Toolbox 与 Zed 的更新逻辑由自身主程序执行。厂商更换组件后需要重新验证。

旧版 Tauri 的例外保留为复测证据。厂商原签名 CC Switch 4.0.30（插件 2.10.0，开发团队 R8UR22V2F9）普通启动两次安装 4.0.38，均报告 `Cross-device link (os error 18)`。退出后，仅该次进程使用外盘专用临时目录，再次点应用内更新成功；从普通原入口冷启动外盘 4.0.38，开发团队相同，严格签名通过。独立测试应用在物理外盘重现插件 2.10.0、2.11.0 跨卷失败，2.14.1 普通启动成功。当前按实际插件版本识别，由[普通入口适配 Tauri 外盘更新](2026-11-21-普通入口适配Tauri外盘更新.md)接续，旧版插件在正常启动时获得同卷临时目录。详细现场保存在本轮本地验证目录 `build/Validation/updater-compat-wUkyrtJ0/REPORT.md`。

Build 82 的扫描回归通过标准入口读取外盘包，覆盖受支持的七款 Sparkle、两款原生 ShipIt、仅确认迁移或守护接手的应用、同框架的其他应用及已不可执行的安装器。关闭守护时，Qoder 的单选仍推荐非锁定迁移，与 DeepSeek Harness 混选时保留手动选择。十个 Tauri 官方插件稳定版本在真实外盘完成更新、冷启动及迁回，并核验两侧列表在守护关闭条件下的可用性。

后续在 `/Volumes/hano/appdisks/AppPorts.noindex/` 上实测 `com.tencent.qq` 与 `com.tencent.QQMusicMac` 的外盘更新：QQ 7.0.2（53644）外盘外壳动态加载沙盒容器内的 `versions/7.0.3-54395/QQUpdate.app` 完成新版运行，`/Applications/QQ.app` 入口与外盘原签名保持完好；QQ 音乐由主程序内置 `UpdateManager` 在外盘原地从 `11.7.0 (73272)` 更新到 `11.11.1 (73285)`，本地入口保持为 stub 并同步刷新至 `11.11.1 (73285)`。两款应用已按 `bundleID` 与自身主可执行文件（`MacOS/QQ`、`MacOS/QQMusic`）登记到 `independentUpdateExecutables`，并通过扫描单测验证；由于 `app-update.yml` 多用于依赖 `ShipIt` 守护接手的 `electron-builder` 应用、`shiply.dylib` 仅为通用配置/资源 SDK，且主程序内置更新器无法静态判断目标路径是否写死 `/Applications/`，这两类模式不外推为默认可用。
