# Agent Note: 微信拆分迁移以账号为入口、以成员保留恢复记录

Status: implemented

## Problem

微信账号目录同时包含高频数据库、高频聊天缩略图与低频大文件视频。用户可能希望迁出全部媒体（`msg + business`），或仅迁出低频冷数据（`msg/file + msg/video`）而把聊天图片与数据库留在内盘。若逐个暴露子目录按钮，会把半迁移状态与父子挂载冲突直接抛给用户，并容易把多开微信的数据交给默认容器判断；若对未放行的微信子目录复用容器骨架的系统保护报错，又会误导用户去自定义目录尝试更深路径（Issue #79、Issue #110）。

## Decision

`PartialWeChatMigrationPolicy` 只接受指定容器 `Data/Documents/xwechat_files` 的直接账号子目录，排除 `all_users`、`config`、`resource`。拆分迁移默认关闭；开启后仅允许两组互斥的精确成员白名单：

- `SplitGroup.media`：`<account>/msg` 与 `<account>/business`
- `SplitGroup.filesAndVideos`：`<account>/msg/file` 与 `<account>/msg/video`

数据库（`db_storage`）、高频图片附件（`msg/attach`）、配置及其他后代绝不进入白名单。部分微信版本可能存在同名普通 SQLite 文件 `msg/file`；`memberMatch(for:)` 与 `existingDirectoryMembers(of:group:)` 均通过 `lstat` 校验 `S_IFDIR`，非目录条目按 `.weChatCompatibility` 拒绝，绝不当作挂载点。`DataDirScanner` 对 `msg` 保持 `mayDiscoverChildren == false`，仅对 `msg/file` 与 `msg/video` 做定点检查，不枚举 `msg/attach` 下的海量哈希子目录。容器标识随实际应用身份传递，账号路径及解析软链接后的路径均须符合策略。

`DataOperationSafety.requirePolicy` 与 `DataDirMover` 保留 `DataPathPolicy.Reason`：命中 `.weChatCompatibility` 时返回微信稳定性专用提示并引导至“应用数据”页的微信账号迁移或拆分迁移，不归入“受 macOS 系统保护”。

界面把同一分组成员聚合为一个账号操作（`WeChatAccountMigrationService.Mode`：`whole`、`split`、`filesAndVideos`），底层各自保留既有 APFS 持久化记录。迁移任意成员之前检查目标组成员的真实目录类型、可迁移资格、受管重叠和完整大小读取；`filesAndVideos` 允许账号下仅存在其中一个真实目录时单独执行，无任何真实目录时拒绝启动。中断后复用已完成成员的挂载记录并继续剩余成员，不把多成员迁移描述为原子提交。`whole`、`split`、`filesAndVideos` 三种模式严格互斥，切换前必须先完整还原；同一账号已有成员的外置根不同也拒绝混用。

还原按当前分组的成员处理准备中、已切换及已回滚待清理的记录，保留部分成员完成、部分成员失败的事实，并在调用 `restoreAndComplete` 前为挂载点计算非缓存目录大小作为 `estimatedTotalBytes`，同时在多成员迁移/恢复分支内为未预设单元的进度对象调用 `configureUnits(_:)` 与逐成员 `setDirectory(_:)`，避免进度条在多成员之间归零跳动。关闭拆分选项不隐藏已有受管记录，也不堵住任意分组的还原出口。

## Alternatives considered

- **整账号迁移**：一个挂载点更容易管理，仍作为 `whole` 模式保留；不能满足数据库或聊天图片留在内盘的拆分需求。
- **允许 `msg` 与 `msg/file` 嵌套叠加挂载**：无需先还原 `msg` 即可把冷数据切到另一外置卷，但父卷卸载、磁盘拔出与重挂顺序会形成跨卷挂载依赖，任一层异常都会遮住或卡死子挂载点；因此强制 `split` 与 `filesAndVideos` 互斥。
- **在目录树中开放任意子目录或月份目录单独迁移**：自由度最高，但会扫描 `msg/attach` 下数百个哈希目录、产生大量 APFS 卷，且会把分散的恢复与模式冲突抛给用户；采用固定分组聚合并保留成员账本。

## Consequences

用户按账号在整账号、`msg + business`、`msg/file + msg/video` 之间三选一，`filesAndVideos` 在释放大文件与视频空间的同时将数据库与 `msg/attach` 聊天图片留在本地。代价是同一分组内的成员仍可能处于不同阶段，界面必须如实显示待完成、缺盘或待解锁，不能合并成虚假的全部成功；两种拆分模式切换必须先完整还原。

外置盘断开时，`msg/file` 与 `msg/video` 空入口同样受 `0500` 只读保护以防止内盘写入分叉；微信在缺盘期间浏览历史文字图片与尝试接收新文件视频的具体客户端表现取决于微信版本，需结合实机验证确认。

## Verification

`PartialWeChatMigrationPolicyTests.swift` 覆盖禁用与启用策略白名单、`msg/file` 为普通 SQLite 文件时的拒绝与单目录回退、`filesAndVideos` 迁移还原及与 `whole`/`split` 的互斥守卫、中断后续传、以及 `.weChatCompatibility` 与 `.systemManagedStructure` 的错误文案区分；`LocalizationAuditTests` 核对 22 种语言的目录键与占位符一致性。外置盘断开状态下微信客户端接收新文件或视频时的交互表现留待实机验证。
