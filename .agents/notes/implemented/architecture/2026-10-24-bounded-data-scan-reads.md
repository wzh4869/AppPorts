# Agent Note: 完整数据扫描以有界并发读取保留原证明契约

Status: implemented

## Problem

微信 APFS 往返的复制前扫描、复制后内容核验及清理明显耗时。真实阶段日志中，2026-10-23 的一次操作复制约 272 秒、验证约 344 秒、清理约 99 秒；入口切换约 3 秒。用户允许真实微信数据测试，明确要求性能优化不能牺牲错误兜底、基线依赖或恢复能力。

## Decision

只调整 `TreeCopySession` 完整扫描内部的读取调度。strictData 在同一目录内最多并发读取 4 个普通文件；目录串行递归，FIFO 和链接保持原路径。含资源叉的普通文件在工作线程属性盘点时退回调用线程重新完整采集，资源叉原有读取、取消和恢复契约继续成立。appBundle 不启用此调度。

每个节点仍按原来的 no-follow 打开、身份/属性稳定性检查、完整 SHA-256、ACL/xattr/时间和最终节点复核生成观察。结果按原枚举顺序归并，硬链接盘点和词法最小组名仍由调用线程更新，父目录末次检查位于全部子项结束后。基线 schema、扫描次数、内容比较、切换/清理顺序、持久化删除检查点及恢复状态机不变；不缓存内容证明或文件状态，不依时间戳跳过读取。

每批只持有有界描述符，全部工作同步结束后才递归、关闭描述符、返回或抛错。工作线程显式继承当前测量、进度和任务控制，但不重新开始阶段。调用任务取消通过批次局部状态传入；已暂停的原控制对象同时被取消以唤醒工作线程。取消对象不存入 DataTransferSession、不传入独立恢复。

## Alternatives considered

- 直接使用原始缓冲区更新 SHA-256：改动更窄，但本机 Release 优化微基准中 2 GiB 内存散列约 0.68–0.74 秒，与当前 ArraySlice 更新没有稳定差异，因此不把它作为主要性能方案。
- APFS 快照/只读稳定源并在复制时建立基线：有机会减少完整读取，但需要改变准备基线的持久化与恢复契约；本轮用户要求保留现有兜底，暂不采用。
- 同时并发目录、资源叉和普通文件：覆盖面更广，但描述符随递归增长，资源叉的直接 Swift Task 取消不能自动传到 Dispatch；本轮收窄为普通文件。
- 删除重复核验、mtime 缓存、后台延后清理：可能更快或更早返回，但改变原证明边界或实际释放空间时间，不满足本轮约束。

## Verification

隔离宿主通过 319 项回归：55 项树/资源叉 XCTest、11 项 noowners Swift Testing、49 项目录迁移/父路径 XCTest 和 204 项挂载、准备恢复、完成、进度、冷恢复、重入及工作流审计 Swift Testing。新增回归比较完整清单、跨目录硬链接、资源叉、精确字节与进度计数，并在工作线程开始读取后验证真正的 Task 取消、暂停/恢复及暂停后取消，检查返回后没有继续读取。源/目标晚写入、MAP_SHARED、删除检查点、冷恢复、部分删除及卷重绑定断言继续通过。

## Consequences

完整扫描在有多个普通文件的目录中能利用更多 CPU 和读取并发，而准备、验证、切换、持久化删除检查点及独立恢复继续依赖原有完整证明。活动树同步和实际复制仍可能占主要时间，小文件组与 business 实测没有明显总体收益；单个文件或每个目录只有一个文件时保持串行。

同步工作线程增加调度及少量状态，冷机械盘的随机读取可能更慢。默认并发上限为 4，任务局部串行覆盖保留用于可比较测试；遇到读取调度回归时可以收回并发，不改变基线格式或恢复契约。原有多遍读取继续存在，非原子观察不获得新的原子安全承诺。源冻结、证明缓存、减少核验或改变同步边界需要新的独立决定。
