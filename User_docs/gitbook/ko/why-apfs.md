# 외장 드라이브가 APFS여야 하는 이유

{% hint style="success" %}
**핵심 내용**

AppPorts 1.9.0부터 `~/Library/Containers/`의 데이터(WeChat 채팅 기록 같은 앱 컨테이너 데이터)를 마이그레이션할 때 외장 드라이브의 APFS 컨테이너에 새 볼륨을 만들고 원래 디렉토리에 직접 연결합니다. 이 방식은 APFS 외장 드라이브에서만 가능합니다. exFAT / NTFS에서는 디스크 이미지를 사용하는 방법도 시험했지만 **드라이브를 뽑자 이미지 전체를 사용할 수 없게 되어** 제공하지 않습니다.

**외장 드라이브가 APFS가 아니어도 바로 바꿀 필요는 없습니다.** 실제 앱과 일반 데이터 디렉토리는 그대로 마이그레이션할 수 있습니다. 컨테이너 데이터만 이 Mac에 두면 앱도 평소처럼 사용할 수 있습니다. 나중에 컨테이너 데이터를 옮기려면 [APFS 외장 드라이브 준비](#prepare-apfs)를 따르세요. exFAT 파티션 안에 여유 공간이 있다고 해서 바로 새 파티션을 만들 수 있는 것은 아닙니다.
{% endhint %}

## 어떤 작업에 필요한가요? <a href="#어떤-작업에-필요한가요" id="어떤-작업에-필요한가요"></a>

| 하려는 작업 | 외장 드라이브 포맷 요구 사항 |
|---|---|
| 실제 앱 마이그레이션(`.app`을 외장 드라이브로 이동) | 제한 없음. exFAT도 가능 |
| 일반 데이터 디렉토리 마이그레이션(`Application Support`, 캐시, `~/.npm` 같은 도구 디렉토리, 사용자 지정 디렉토리) | 제한 없음 |
| **컨테이너 데이터** 마이그레이션(`~/Library/Containers/`, `~/Library/Group Containers/`; WeChat, QQ Music, App Store 앱의 데이터가 있는 위치) | **APFS 필수** |

세 번째 종류에만 적용됩니다. 다만 이 종류에는 용량이 커서 가장 옮기고 싶은 데이터가 많습니다.

## 컨테이너 데이터는 왜 특별한가요? <a href="#컨테이너-데이터는-왜-특별한가요" id="컨테이너-데이터는-왜-특별한가요"></a>

대부분의 Mac 앱은 샌드박스 앱입니다. 시스템이 앱마다 `~/Library/Containers/` 아래에 전용 폴더를 배정하고, 앱은 자기 폴더 안에서만 읽고 쓸 수 있습니다. 이는 macOS의 보안 설계이며 App Store에 배포되는 앱의 필수 조건입니다.

예전 AppPorts는 폴더를 외장 드라이브에 복사한 뒤 원래 위치에 그곳을 가리키는 ‘바로가기’(심볼릭 링크)를 남겼습니다. 일반 데이터 디렉토리에는 잘 작동하지만 샌드박스 앱에서는 **처음부터 제대로 작동한 적이 없습니다**.

- 시스템은 바로가기의 위치가 아니라 **가리키는 대상**을 검사합니다. 외장 드라이브를 가리키면 전용 폴더를 벗어나는 것이므로 접근을 거부합니다.
- 예전에 작동하는 것처럼 보인 이유는 마이그레이션 중 ‘재서명’을 추가로 수행해 앱의 샌드박스 신원을 제거했기 때문입니다. 더 이상 샌드박스 앱이 아니므로 제한도 받지 않았습니다.
- macOS 27에서 그 대가가 나타나기 시작했습니다. 시스템이 이 앱에 이 폴더에 접근할 자격이 있는지 확인할 때, 신원을 제거한 앱이 일치하지 않아 이중 클릭 후 1초 만에 종료될 수 있습니다. WeChat에서 확인했으며 QQ Music은 현재 열립니다. 해결하려면 앱을 재설치해야 합니다. 배경은 [macOS 27 업그레이드 안내](macos-27.md)를 참고하세요.

새 방식의 핵심 조건은 하나입니다. **데이터는 외장 드라이브에 있으면서도 전용 폴더를 ‘벗어나지’ 않아야 합니다.**

## 새 방식은 어떻게 해결하나요? <a href="#새-방식은-어떻게-해결하나요" id="새-방식은-어떻게-해결하나요"></a>

바로가기 대신 외장 드라이브의 공간을 **원래 폴더에 직접 마운트**합니다. 폴더의 위치는 그대로인데 그 ‘바닥’만 외장 드라이브로 바뀐다고 생각하면 됩니다.

- 앱에 보이는 경로는 한 글자도 바뀌지 않으므로 시스템 검사도 그대로 통과합니다.
- 앱 서명은 한 바이트도 변경하지 않습니다. 재서명이 필요 없고 이후 시스템 업그레이드에서도 이로 인한 문제가 생기지 않습니다.
- 외장 드라이브가 없으면 폴더는 비어 있습니다. 앱은 데이터가 없는 것으로 처리하며, 새 데이터를 이 Mac에 써서 두 사본을 만들지 않습니다.

특정 폴더에 공간을 마운트하려면 그 공간이 독립된 **볼륨**이어야 합니다. APFS는 **하나의 APFS 컨테이너에 여러 볼륨을 추가하고 컨테이너의 남은 공간을 함께 사용할 수 있습니다**. 볼륨별 크기를 미리 정하거나 다시 파티션할 필요가 없습니다. AppPorts는 이 기능으로 마이그레이션하는 디렉토리마다 전용 볼륨을 만듭니다. ‘볼륨 추가’와 물리 디스크에 새 파티션을 만드는 것은 서로 다른 작업입니다.

exFAT나 NTFS 파티션 안에는 이런 방식으로 APFS 볼륨을 추가할 수 없습니다. 같은 드라이브에 기존 포맷과 APFS를 함께 유지하려면 APFS 전용 파티션이 필요합니다. 이미 있는 미할당 공간을 사용하거나, 기존 파일 시스템을 지원하는 도구로 원래 파티션을 먼저 줄여야 합니다. 불가능하면 백업 후 다시 파티션해야 합니다. AppPorts가 사용자를 대신해 디스크 파티션을 조정하지는 않습니다.

## 다른 방법도 시험했지만 실패했습니다 <a href="#다른-방법도-시험했지만-실패했습니다" id="다른-방법도-시험했지만-실패했습니다"></a>

exFAT 사용자도 많아 우회 방법을 진지하게 검토했습니다. exFAT 드라이브에 디스크 이미지 파일(sparsebundle, Time Machine이 네트워크 드라이브에 백업할 때 사용하는 형식)을 두고, 그 안을 APFS로 만든 뒤 이미지를 폴더에 마운트하는 방법입니다.

처음에는 좋아 보였습니다. 2026년 9월 macOS 27에서 시험한 결과는 다음과 같습니다.

- APFS 드라이브가 필요 없고 어떤 포맷에도 저장할 수 있습니다.
- 앱이 처음 접근할 때 ‘이동식 볼륨 접근’ 권한 창이 나타나지 않습니다. APFS 볼륨 방식에서는 한 번 나타납니다.
- 읽기와 쓰기 속도는 APFS 볼륨과 비슷합니다.
- 스티커 같은 시스템 플랫폼 앱도 사용할 수 있습니다. APFS 볼륨 방식은 플랫폼 앱에서 작동하지 않습니다.

그다음 실제 사용에 가까운 시험을 했습니다. **데이터를 쓰는 도중 드라이브를 바로 뽑았습니다.** 64 GB USB 드라이브를 APFS로 포맷하고 그 위에 APFS 볼륨과 디스크 이미지를 하나씩 만든 다음 각각 폴더에 마운트했습니다. 두 프로그램이 계속 데이터베이스를 기록하게 했습니다. WeChat과 QQ Music이 채팅 기록이나 재생목록을 저장하는 방식과 같습니다. 10여 초 뒤 USB 드라이브를 뽑고 다시 연결해 남은 내용을 확인했습니다.

| | 분리 전에 기록한 데이터 | 다시 연결한 결과 |
|---|---|---|
| APFS 볼륨, 1차(일반 쓰기) | 7177개 레코드 | 데이터베이스 손상이 한 번 보고되었지만 복구 명령으로 7172개를 모두 복구. 파일 시스템은 정상 |
| APFS 볼륨, 2차(앱에서 디스크 쓰기 강제) | 1906개 레코드 | 1905개 정상. 마지막 1개만 손실 |
| 디스크 이미지, 1차(일반 쓰기) | 25574개 레코드 | **이미지가 열리지 않음**. 내부 데이터 전체에 접근 불가 |
| 디스크 이미지, 2차(앱에서 디스크 쓰기 강제) | 373개 레코드 | **여전히 이미지가 열리지 않음** |

차이는 ‘조금 더 잃느냐’가 아니라 ‘몇 개를 잃느냐, 전부 접근할 수 없게 되느냐’였습니다.

이유는 복잡하지 않습니다. 디스크 이미지는 외장 드라이브의 8 MB 파일 여러 개로 구성됩니다. 이미지 자체의 ‘목차’는 첫 번째 파일에 있으며 몇 초마다 다시 기록됩니다. 드라이브를 뽑을 때 외장 파일 시스템은 파일 자체의 무결성만 보장하며, 파일 안에 쓰다 만 내용의 완전성까지 보장하지 않습니다. 목차를 절반만 쓴 순간 끊기면 이미지 전체가 목차 없는 조각이 됩니다. 앱이 디스크 쓰기를 아무리 강제해도 소용없습니다. 이 부분은 이미지 자체의 문제라 앱이 제어할 수 없습니다.

Time Machine으로 네트워크 드라이브에 백업하다가 ‘백업이 손상되어 새 백업을 만들어야 한다’는 안내를 본 적이 있다면 같은 문제입니다. 백업은 다시 만들 수 있지만 채팅 기록은 그럴 수 없습니다.

그래서 시험 후 디스크 이미지 방식은 제외했습니다. 데이터 마이그레이션 도구가 ‘한 번 뽑으면 전부 사라질 수 있는’ 선택지를 제공해서는 안 됩니다. 다른 면에서 더 편리하더라도 마찬가지입니다.

## 지금 어떻게 하면 되나요? <a href="#what-to-do" id="what-to-do"></a>

먼저 **옮기려는 것이 컨테이너 데이터인지** 확인하세요. 아니라면 아무것도 바꿀 필요가 없습니다. 맞다면 외장 드라이브 상태에 따라 선택하세요.

| 상황 | 권장 방법 |
|---|---|
| 이미 암호화되지 않은 APFS 드라이브 | ‘앱 데이터’에서 ‘마운트 마이그레이션’ 클릭 |
| exFAT / NTFS 드라이브를 바꾸고 싶지 않음 | **그대로 유지**: 컨테이너 데이터는 이 Mac에 두고 다른 항목은 평소처럼 마이그레이션. 정상적인 사용 방식입니다 |
| 다른 APFS 드라이브가 있거나 별도로 준비할 수 있음 | AppPorts에서 외장 저장 장치를 해당 드라이브로 바꾼 뒤 컨테이너 데이터 마이그레이션 |
| 현재 드라이브에 APFS 공간을 만들고 싶음 | 먼저 백업한 뒤 아래 [APFS 외장 드라이브 준비](#prepare-apfs) 참고 |
| 암호화된 APFS 드라이브 | 아직 지원하지 않음. 아래 [암호화된 외장 드라이브](#encrypted-drives) 참고 |

잘 모르겠다면 AppPorts에서 ‘마운트 마이그레이션’을 한 번 눌러보세요. 먼저 외장 저장 장치를 읽기 전용으로 검사해 현재 상황을 알려줍니다. 아무것도 변경하지 않습니다.

**외장 드라이브 포맷 확인:** Finder에서 드라이브를 선택하고 `⌘ I`를 누른 뒤 ‘포맷’을 확인하세요. ‘APFS’면 사용할 수 있습니다. ‘ExFAT’, ‘NTFS’, ‘Mac OS 확장’(HFS+)이면 위 표의 두 번째 경우입니다.

## APFS 외장 드라이브 준비 <a href="#prepare-apfs" id="prepare-apfs"></a>

{% hint style="warning" %}
**디스크를 변경하기 전에**

아래 어떤 방법을 사용하든 먼저 드라이브의 데이터를 백업하세요. AppPorts가 대신 지우거나 파티션을 조정하지 않습니다.
{% endhint %}

**중요한 데이터가 없는 드라이브:** ‘디스크 유틸리티’에서 드라이브를 선택하고 ‘지우기’를 누르세요. 포맷은 ‘APFS’, 설계는 ‘GUID 파티션 맵’을 선택합니다. 지우면 드라이브 전체가 비워집니다.

**데이터와 기존 파티션을 유지하려는 경우:** 먼저 ‘GUID 파티션 맵’을 사용하는지 확인한 뒤 다음 경우를 구분하세요. Finder의 ‘사용 가능’ 용량은 파일 시스템 안의 남은 용량이며 **파티션 바깥의 미할당 공간과 다릅니다**.

| 현재 상황 | APFS 공간 준비 방법 |
|---|---|
| 기존 APFS 컨테이너가 있음 | AppPorts에서 그 안의 볼륨을 선택하면 됩니다. 마이그레이션용 APFS 볼륨을 자동으로 추가하므로 다시 파티션할 필요가 없습니다 |
| 새 파티션에 사용할 수 있는 충분한 미할당 공간이 있음 | 기존 파티션을 지우지 않고 해당 공간에 APFS 파티션을 만들 수 있습니다. 작업 전 디스크 유틸리티가 표시하는 변경 범위를 확인하세요 |
| exFAT가 드라이브 전체를 차지하며 미할당 공간이 없음 | macOS 디스크 유틸리티와 Windows 기본 디스크 관리는 모두 exFAT를 줄일 수 없습니다. 기본 도구를 쓴다면 먼저 백업하고, 지운 뒤 다시 파티션하고, 마지막으로 파일을 복원해야 합니다 |
| NTFS 파티션이며 미할당 공간이 없음 | macOS는 NTFS를 무손실로 줄일 수 없습니다. Windows 디스크 관리에서 먼저 NTFS를 줄여 미할당 공간을 확보한 뒤 macOS로 돌아와 APFS 파티션을 만들 수 있습니다. 줄일 수 있는 크기는 파일 배치 등의 조건에 따라 제한됩니다 |
| Mac OS 확장(저널링 HFS+) 파티션 또는 APFS 컨테이너 | macOS가 무손실 크기 조정을 지원합니다. 공간과 파티션 배치 조건을 충족하면 줄인 뒤 APFS 파티션을 만들 수 있습니다. 그래도 먼저 백업하세요 |

GUID 파티션 맵이 아니라면 위의 새 파티션 추가 절차를 그대로 적용하지 마세요. 먼저 백업한 뒤 GUID 설계로 다시 파티션해야 합니다. 준비가 끝나면 AppPorts의 외장 저장 장치 경로를 APFS 볼륨으로 지정하세요.

근거: 이 Mac의 `man diskutil`에서 `resizeVolume`은 **journaled HFS+**를 요구합니다. APFS는 `apfs resizeContainer`를 사용합니다. [Microsoft의 기본 볼륨 축소 안내](https://learn.microsoft.com/en-us/windows-server/storage/disk-management/shrink-a-basic-volume)는 Windows 기본 도구가 지원하는 대상을 NTFS 또는 파일 시스템이 없는 볼륨으로 명시하며 exFAT는 포함하지 않습니다. 타사 도구의 exFAT 무손실 축소 지원 여부는 별도로 확인해야 하며 기본 시스템 기능으로 간주해서는 안 됩니다.

**Windows에서도 함께 쓸 드라이브:** Windows는 기본적으로 APFS를 읽고 쓸 수 없습니다. exFAT와 APFS 파티션 두 개를 만들어 전자는 Windows와 공유하고 후자는 AppPorts에 사용할 수 있습니다. exFAT가 이미 전체를 차지하고 있다면 기본 도구로 바로 APFS 파티션을 떼어낼 수 없으므로 먼저 백업한 뒤 다시 파티션해야 합니다.

## 암호화된 외장 드라이브 <a href="#encrypted-drives" id="encrypted-drives"></a>

마운트 마이그레이션은 외장 드라이브의 APFS 컨테이너에 새 데이터 볼륨을 만듭니다. 새 볼륨은 원래 볼륨의 암호를 **상속하지 않습니다**. 그대로 옮기면 이 Mac에서 FileVault로 보호되던 채팅 기록이 누구나 연결하면 읽을 수 있는 볼륨에 저장됩니다. 로그인 시 자동 잠금 해제와 암호 관리가 완성되기 전까지 AppPorts는 암호화된 APFS 드라이브에 마운트 마이그레이션을 제공하지 않으며, 몰래 암호화되지 않은 볼륨을 만들지도 않습니다.

가능한 방법:

- **그대로 유지:** 컨테이너 데이터를 이 Mac에 두어 FileVault 보호를 계속 받습니다.
- **암호화되지 않은 APFS 드라이브나 파티션으로 변경:** 해당 데이터가 외장 드라이브에서 암호화되지 않는다는 점을 이해한 뒤 마이그레이션합니다.

## 클래식 데이터 마이그레이션 모드 <a href="#클래식-데이터-마이그레이션-모드" id="클래식-데이터-마이그레이션-모드"></a>

설정의 클래식 데이터 마이그레이션 모드는 1.8.1의 심볼릭 링크와 재서명 방식을 되살립니다. APFS가 필요 없지만 기존 방식의 위험도 그대로 있습니다. 샌드박스 앱이 macOS 27에서 열리지 않거나 로그인 상태가 사라질 수 있습니다. 이미 기존 방식에 의존하는 사용자만을 위해 남겨 둔 기능이며 **APFS 요구 사항을 피하려고 켜는 것은 권장하지 않습니다**. 자세한 내용은 [설정](settings.md#classic-data-migration-mode)을 참고하세요.

## 자주 묻는 질문 <a href="#자주-묻는-질문" id="자주-묻는-질문"></a>

### 예전에 exFAT로 옮긴 컨테이너 데이터는 어떻게 하나요? <a href="#예전에-exfat로-옮긴-컨테이너-데이터는-어떻게-하나요" id="예전에-exfat로-옮긴-컨테이너-데이터는-어떻게-하나요"></a>

예전 마이그레이션은 바로가기와 재서명을 사용해 드라이브 포맷과 무관했습니다. 문제는 포맷이 아니라 재서명입니다. 해결 방법은 [macOS 27 업그레이드 안내](macos-27.md)를 참고하세요. 처리 후에도 컨테이너 데이터를 외장 드라이브에 두려면 [APFS 외장 드라이브 준비](#prepare-apfs)를 따르세요.

### exFAT에 ‘위험을 이해했습니다’ 선택지를 제공하지 않는 이유는 무엇인가요? <a href="#exfat에-위험을-이해했습니다-선택지를-제공하지-않는-이유는-무엇인가요" id="exfat에-위험을-이해했습니다-선택지를-제공하지-않는-이유는-무엇인가요"></a>

이 위험은 가끔 조금 잃는 것이 아니라 한 번 뽑으면 전부 접근할 수 없게 되는 것입니다. 드라이브 분리는 이동식 드라이브의 아주 일반적인 사용 방식입니다. 채팅 기록을 실제로 잃은 뒤에는 ‘미리 알렸다’는 말이 아무 도움이 되지 않습니다.

### APFS로 바꾸면 읽기와 쓰기 속도에 영향이 있나요? <a href="#apfs로-바꾸면-읽기와-쓰기-속도에-영향이-있나요" id="apfs로-바꾸면-읽기와-쓰기-속도에-영향이-있나요"></a>

없습니다. APFS는 macOS의 기본 포맷이며 SSD에서는 보통 exFAT보다 빠릅니다. 같은 USB 드라이브에서 진행한 시험에서는 APFS 볼륨의 데이터베이스 쓰기가 exFAT에 직접 쓰는 것보다 약 10배 빨랐습니다.

### HFS+(Mac OS 확장)도 가능한가요? <a href="#hfs-mac-os-확장-도-가능한가요" id="hfs-mac-os-확장-도-가능한가요"></a>

마운트 마이그레이션에 직접 사용할 수는 없습니다. HFS+에는 APFS처럼 여러 볼륨이 공간을 공유하는 기능이 없습니다. 다만 저널링 HFS+는 macOS 기본 도구로 무손실 축소할 수 있으므로 조건이 맞으면 새 APFS 파티션을 위한 공간을 확보할 수 있습니다. 이 점은 exFAT와 다릅니다. 작업 전 백업은 여전히 필요합니다. 위 [APFS 외장 드라이브 준비](#prepare-apfs)를 참고하세요.
