# AppPorts 怎么判断应用迁移后能否更新

同样是把应用迁到外盘，IINA 可以在原地装好新版，有的应用却会把新版装回本机。应用列表里的「可用」回答的是**迁移后有没有已确认的更新方式**。想知道今天有没有新版，仍要看应用自己的“检查更新”或 App Store。AppPorts [设置里的“检查更新”](/docs/settings#updates)查的是 AppPorts 自己。

本文的徽章和推荐规则依据 2026 年 11 月 21 日的 AppPorts 2.3.1 候选构建（build 82）。11 月 22 日，我们又在 build 84 上核对了守护接手后的任务记录与日志；这些徽章、悬停与独立更新识别能力（包括新增的 QQ 与 QQ 音乐）已随 2.4.0 正式发布。你可以在设置中查看正在使用的构建号。

## 列表为什么显示「检测中」「可用」或「未知」 {#badges}

本机“应用程序”里可能只留了一个启动入口。AppPorts 会沿入口找到实际应用包，再判断它使用的更新组件、所在位置和锁定状态。点击应用名称下方排在首位的更新徽章，可以查看这款应用的判断依据；将指针停在徽章上约 0.25 秒，也能查看同一份说明。[徽章与状态](/docs/badges#apps)

| 实际情况 | 列表怎样判断 |
| --- | --- |
| 使用 Sparkle 更新组件、且已实测能自行更新外盘副本的应用 | 网易云音乐、IINA、Keka、CotEditor、Transmission、Mac Performance Monitor 和 PortKiller 的非商店版在应用标识和实测安装组件匹配时显示「可用」，关闭守护仍可更新。 |
| 使用内置安装器（ShipIt）并已实测自行完成安装的应用 | Qoder、OpenCode 在实测中由自带的安装器（ShipIt）完成安装。匹配该组件时显示「可用」，守护就绪后还可尝试处理安装失败。 |
| 其他已识别到常见内置更新组件（Sparkle / Squirrel / ShipIt）的应用 | 目前只确认了更新框架或守护协助路径。守护就绪时显示「可用」，启动时显示「检测中」，关闭时显示「未知」。WorkBuddy 已确认可迁移，DeepSeek Harness 有守护接手成功的记录。 |
| 只认出 Electron，或只找到一个名字带 updater 的文件 | 显示「未知」。Electron 应用可以选择不同的安装方式，单凭这一线索无法判断新版会写到哪里。 |
| Mac App Store 应用 | 在 macOS 15.1 及以上，有商店收据且外盘副本位于商店配置的那块盘的 `Applications` 目录时显示「可用」。本机商店应用即将迁往该目录时也可预先显示。通过 App Store 更新，无需开启守护。 |
| 已实测能独立更新外盘副本 | Firefox、Thunderbird、Google Chrome、JetBrains Toolbox、Zed、DMG Canvas、Querious、Screenflick、QQ 和 QQ 音乐的 Mac 版：应用标识和随包程序匹配时，非锁定迁移后显示「可用」，关闭更新守护也可以在应用内更新。 |
| Tauri 官方更新插件 | 平时从「应用程序」或原来固定在 Dock 的图标打开，照常在应用内更新。AppPorts 能识别标准发行包内的插件版本。2.10.0 至 2.13.1 由本机入口自动提供同卷临时目录，2.13.2 起的 2.x 版本由插件自行选择。两种方式均可在关闭守护时工作。 |
| 使用其他更新器 | 只有已验证能独立更新外盘副本，或能先更新到本机再迁出的应用，才会按该方式标「可用」。未验证的显示「未知」。 |

旧版 Tauri 插件需要从本机入口启动。AppPorts 会把已有的 Dock 固定项指向这个入口，保留图标顺序。启动时 Dock 可能短暂显示两个图标。直接双击外盘里的旧版应用会跳过这项适配。

这三款的确认依据各有不同。网易云音乐有非锁定迁移后通过自身 Sparkle 更新成功的记录；WorkBuddy 使用 Squirrel/ShipIt，由维护者人工确认；DeepSeek Harness 则有守护接手后从本机原入口打开外盘新版的实测记录。后文列出了那次测试的具体版本。

## 非锁定、锁定和「待迁出」怎么选 {#migration}

需要选择迁移模式时，「可用」的应用会推荐**非锁定迁移**，按回车即可选中。混合迁移一批应用时，需要选择模式的每款应用都可用，才会推荐这一项。「检测中」或「未知」时由你手动选择。网易云音乐和 WorkBuddy 沿用普通迁移流程，直接迁移即可。

已经锁定的外盘应用显示「锁定迁移」。想更新时，可先迁回本机，更新后再迁出。如果更新器自行把 1.1 装回本机，外盘还留着 1.0，刷新后会优先看到「待迁出」。核对版本，点“迁移到外部”，就能把本机新版迁回外盘。一次版本差异也可能来自手动安装，因此不会让同款应用永久获得「可用」徽章。[应用更新与迁出操作](/docs/core#updates)

## 应用自带的更新器安装失败后，守护怎样接手 {#guardian}

在“设置 → 后台代理”开启“应用更新守护”后，即使退出 AppPorts 主窗口，守护也可以在后台处理。第三方应用照常检查和下载自己的新版。当应用下载完新版，却在交给内置安装器（常见如 Electron 应用里负责把新版装进磁盘、日志中常记作 ShipIt 的组件）执行安装这一步失败时，守护会对已迁移且有记录的应用按下面的顺序核对现场并尝试接手。

1. **确认是哪一笔安装。** 本机入口、外盘卷和应用路径必须对应迁移记录。守护将应用自带安装器（ShipIt）的更新请求与最近一次安装尝试的目标、错误和退出记录对应起来。它最多读取日志末尾的 1 MiB；几天前的失败不能作为接手今天更新的依据。
2. **确认外盘可以写入、缓存新版可以使用。** 守护核对应用标识与开发者签名。如果外盘旧版还在，也会核对同一开发者和版本先后。安装器仍在运行或其他操作正在占用相关文件时会等待。关键证据缺失时保留现有副本。
3. **安装并核对结果。** 守护先验证准备好的新版，再安装到原外盘位置。替换已有旧版时会保留旧包，随后刷新仍然存在的本机入口。任务中心会在同一条“应用更新恢复”记录里显示本次接手的进度和结果。同一份新版连续两次未通过签名校验时，守护会核验旧版，等应用和更新器退出后自动回退。原入口刷新成功后，守护清理本次被拒的新版和已确认的临时副本。找不到可核验的旧版时，任务中心会说明原因并保留恢复材料。

**怎样确认 AppPorts 接过手？** 打开「任务中心」，找到「应用更新恢复 · 应用名」。结果显示「已接手成功」，就说明守护完成了这次恢复。如果当时开启了日志记录，可在「设置 → 日志设置」选择「在 Finder 中查看」，在 `AppPorts_Log.txt` 中搜索 `已自动完成 ShipIt 更新恢复`。对照时间和下一行的 `bundle_id`，就能核对是哪款应用。[日志设置](/docs/settings#logs)

一次普通的内置更新，或由应用自带安装器自己顺利完成的更新，都可能无需 AppPorts 介入。因此，任务中心没有“应用更新恢复”记录时，可以退出应用，从原来的本机入口重开，核对实际运行的版本。[任务状态与恢复](/docs/migration-strategy/portal#updates)

## 更新 AppPorts 后，守护怎么接班 {#handoff}

AppPorts 在应用内安装自身新版前会先暂停旧守护。安装取消或安装程序启动失败时，会恢复此前暂停的守护。用 DMG 或 ZIP 手动替换时，打开一次新版 AppPorts，它会同步后台服务。原先关闭了守护的用户，升级后仍保持关闭。

新版主窗口打开时，守护可能还在启动。只有确认监听已开始，运行进程、可执行文件和构建号都与当前 AppPorts 对应，依赖守护的应用才会重新显示「可用」。等待期间显示「检测中」，徽章会自动刷新。若设置持续提示守护尚未就绪，可到“后台代理”点击“重试”。[后台代理设置](/docs/settings)

在 macOS 15.7.7 的隔离测试中，build 80 通过应用内安装流程换成已准备好的 build 81 后，新守护自动启动。我们用两份原签名 DeepSeek Harness 和一份超过 64 MiB 的日志重现已知的安装失败。新守护把外盘 0.2.1-rc.2 更新到 0.2.2-rc.5，任务中心只出现一条成功记录，从原本机入口冷启动也打开了外盘 rc.5。该测试使用预先准备的候选包和失败记录，正式更新源没有发布这次构建。

## 外盘更新实测 {#examples}

2026 年 11 月 21 日，IINA 在非锁定迁移后通过 Sparkle 从 **1.3.5 更新到 1.5.1**。退出后从本机原入口冷启动，实际运行的是外盘 1.5.1。这是应用自行完成更新的例子。

在关闭更新守护的 macOS 15.7.7 测试机上，Firefox 从 160.0 更新到 160.0.1，Google Chrome 从 153.0.8010.48 更新到 158.0.8127.37。退出再从本机原入口打开，运行的都是外盘新版，开发者签名有效。

CC Switch 4.0.30 在隔离测试中通过同卷临时目录成功更新到 4.0.38，从原入口重新打开后，运行的是带厂商签名的外盘新版。旧版 AppPorts 创建的标准入口会在应用列表扫描时自动刷新，下次照常启动即可生效。直接打开外盘应用或通过传统符号链接启动时，旧插件使用系统默认临时目录。

Clash Verge 默认保留在本机。在隔离环境把 2.5.5 放到外盘后，它启动时要求移回本机，选择取消就会退出。

同日，DeepSeek Harness 从 **0.2.2-rc.3 更新到 rc.5** 时，ShipIt 安装失败并退出。它的日志已积累约 64 MiB，原守护读不到本次结果。复测时，单独启动的修复版守护从日志末尾识别出这一次失败，完成外盘安装，任务中心显示“已接手成功”。退出后从原入口打开，运行的是外盘 rc.5。这次验证了该安装请求和缓存组合；仅凭另一款应用也带有 ShipIt，还需要检查它本次失败时留下了哪些材料。
