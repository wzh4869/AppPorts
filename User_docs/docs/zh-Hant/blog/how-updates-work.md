# AppPorts 如何判斷應用程式遷移後能否更新

同樣是把應用程式遷到外接磁碟，IINA 可以在原處裝好新版，有些應用程式卻會把新版裝回 Mac。列表裡的「可用」回答的是**遷移後是否有已確認的更新方式**。想知道今天有沒有新版，仍要用應用程式自己的更新功能或到 App Store 查詢。AppPorts 設定裡的「檢查更新」查的是 AppPorts 本身。

本文的徽章與遷移建議以 2026 年 11 月 21 日的 AppPorts 2.3.1 候選版本（build 82）為例。11 月 22 日，我們也在 build 84 核對了守護介入後的任務記錄與日誌；這些徽章、懸停與獨立更新辨識能力（包含新增的 QQ 與 QQ 音樂）已隨 2.4.0 正式發佈。你可以在設定中查看目前的組建編號。

## 「檢查更新」查的是什麼 {#appports}

開啟 AppPorts 主介面時會檢查官方版本資訊，也可以在設定裡手動點選「檢查更新」。AppPorts 逐段比較官方清單 `latest.json` 裡的版本號與目前執行的版本。例如兩者都是 2.3.1，單獨將 build 從 80 調到 81 不會觸發更新提示。手動檢查時，無法連線到更新來源會顯示檢查失敗；檢查成功且未發現更高的正式版本時，會顯示已是最新版本。

發現新版後，可以選擇國內來源或 GitHub 下載對應版本。AppPorts 會核對套件大小、SHA-256、應用程式識別碼、版本、架構及最低系統需求。點選「安裝並重新啟動」才會開始替換。若正在遷移或復原應用程式，請等工作結束再安裝。[設定裡的更新入口](/docs/settings#updates)

## 列表為什麼顯示「檢測中」「可用」或「未知」 {#badges}

Mac 的「應用程式」資料夾裡可能只留有啟動入口。AppPorts 會沿入口找到實際的應用程式套件，再判斷其更新元件、所在位置和鎖定狀態。點選應用程式名稱下方排在首位的更新徽章，即可查看判斷依據；將游標停在徽章上約 0.25 秒，也能查看同一份說明。[徽章與狀態](/docs/badges#apps)

| AppPorts 找到了什麼 | 列表如何判斷 |
| --- | --- |
| 已自行更新外接磁碟副本的 Sparkle 應用程式 | 網易雲音樂、IINA、Keka、CotEditor、Transmission、Mac Performance Monitor 和 PortKiller 的非商店版，在應用程式識別碼與實測安裝元件相符時顯示「可用」，關閉守護也能更新。 |
| 已自行完成安裝的 ShipIt 應用程式 | Qoder、OpenCode 在實測中透過隨附的 ShipIt 完成安裝。元件相符時顯示「可用」，守護就緒後也能嘗試處理安裝失敗。 |
| 其他已辨識的 Sparkle 或 Squirrel/ShipIt 應用程式 | 目前只確認了更新框架或透過守護復原的方式。守護就緒時顯示「可用」，啟動時顯示「檢測中」，關閉時顯示「未知」。WorkBuddy 已確認可遷移，DeepSeek Harness 有守護接手成功的記錄。 |
| 只有 Electron，或只有名稱含 updater 的檔案 | 顯示「未知」。Electron 應用程式可以使用不同的安裝工具，單憑這項線索無法判斷新版會裝到哪裡。 |
| Mac App Store 應用程式 | 在 macOS 15.1 或以上版本，有商店收據，且外接磁碟副本位於商店設定的磁碟 `Applications` 資料夾時顯示「可用」。即將遷往該目錄的本機商店應用程式也可預先顯示。透過 App Store 更新，無需開啟守護。 |
| 已實測能獨立更新外接磁碟副本 | Firefox、Thunderbird、Google Chrome、JetBrains Toolbox、Zed、DMG Canvas、Querious、Screenflick、QQ 和 QQ 音樂的 Mac 版，應用程式識別碼及隨附程式相符時，非鎖定遷移後顯示「可用」。關閉更新守護也可以在應用程式內更新。 |
| Tauri 官方更新外掛程式 | 照常從「應用程式」或原先固定在 Dock 的圖示開啟，再於程式內更新。AppPorts 可辨識標準發行套件內的外掛程式版本。2.10.0 至 2.13.1 會由本機入口自動提供同卷暫存目錄，2.13.2 起的 2.x 版本則由外掛程式自行選擇。關閉守護也能使用這兩種方式。 |
| 使用其他更新器 | 只有經實測確認能獨立更新外接磁碟副本，或能先更新至本機再遷出的應用程式，才會依該方式標為「可用」。尚未驗證的顯示「未知」。 |

舊版 Tauri 外掛程式需要從本機入口啟動。AppPorts 會將現有的 Dock 固定項目指向這個入口，保留圖示順序。啟動時 Dock 可能短暫顯示兩個圖示。直接按兩下外接磁碟上的舊版應用程式會略過這項適配。

三款應用程式的確認依據各有不同。網易雲音樂有非鎖定遷移後透過自身 Sparkle 成功更新的記錄；WorkBuddy 使用 Squirrel/ShipIt，由維護者人工確認；DeepSeek Harness 則有守護接手後，從原本的本機入口啟動外接磁碟新版的實測記錄。下文列出該次測試的版本。

## 如何選擇遷移模式及處理「待遷出」 {#migration}

需要選擇模式時，「可用」的應用程式會顯示**「不鎖定遷移（建議）」**，按 Return 即可選取。批次遷移時，所有需要選擇模式的應用程式都可用，才會推薦這一項。顯示「檢測中」或「未知」時，由你手動選擇。網易雲音樂和 WorkBuddy 沿用一般遷移流程，直接遷移即可。

已鎖定的外接磁碟應用程式顯示「鎖定遷移」。可先遷回本機，更新後再遷出。如果更新器把 1.1 版裝回本機，而外接磁碟仍是 1.0，重新整理後會優先看到「待遷出」。核對版本，選擇「遷移到外部」，即可把本機新版移回外接磁碟。一次版本差異也可能來自手動安裝，因此同款應用程式不會就此永久取得「可用」徽章。[應用程式更新與遷出操作](/docs/core#updates)

## ShipIt 安裝失敗後，守護如何接手 {#guardian}

在「設定 → 背景代理」開啟「應用程式更新守護」後，即使結束 AppPorts 主程式，守護也可在背景工作。第三方應用程式照常自行檢查及下載新版。對於已留下遷移記錄的應用程式，守護會依序核對以下事項。

1. **確認是哪一次安裝。** 本機入口、外接卷和目標路徑必須符合遷移記錄。守護會將 ShipIt 請求與最近一次安裝嘗試的目標、錯誤及結束記錄對照。最多讀取日誌末尾的 1 MiB，幾天前的失敗不足以成為接手今天更新的依據。
2. **確認目標可寫入、快取的新版可使用。** 守護核對應用程式識別碼和開發者簽章。外接磁碟上若還有舊版，也會核對開發者是否相同及版本先後。安裝程式仍在執行，或其他操作正在使用相關檔案時，守護會等候。缺少關鍵證據時保留現有副本。
3. **安裝並驗證結果。** 守護先驗證準備好的新版，再裝到原來的外接磁碟路徑。替換既有舊版時會保留舊套件，並重新整理仍存在的本機入口。「任務中心」會在同一筆「應用程式更新恢復」記錄中顯示本次復原的進度與結果。同一份新版連續兩次未通過簽章驗證時，守護會驗證舊版，等應用程式與安裝程式結束後自動復原。重新整理本機入口後，守護會清除本次遭拒的新版和可確認的暫存副本。找不到可驗證的舊版時，任務中心會說明原因並保留復原所需的檔案。

**如何確認 AppPorts 曾經介入？** 開啟「任務中心」，找到該應用程式的「應用程式更新恢復」記錄。「已接手成功」表示守護已完成這次復原。如果當時已開啟日誌記錄，可在「設定 → 日誌設定」選擇「在 Finder 中查看」，並在 `AppPorts_Log.txt` 搜尋日誌原文 `已自动完成 ShipIt 更新恢复`。對照時間及下一行的 `bundle_id`，即可確認是哪個應用程式。[日誌設定](/docs/settings#logs)

一般的 Sparkle 更新，或由 ShipIt 順利完成的安裝，都可能無需守護介入。如果任務中心沒有更新復原記錄，可以結束應用程式，從原本的本機入口重新開啟，核對實際執行的版本。[更新保護與復原](/docs/migration-strategy/portal#updates)

## 更新 AppPorts 後，守護如何交接 {#handoff}

AppPorts 在安裝自身新版前會先暫停舊守護。取消安裝或安裝程式啟動失敗時，會恢復先前暫停的守護。若使用 DMG 或 ZIP 手動替換，請開啟一次新版 AppPorts，讓它同步背景服務。原先關閉守護的使用者，升級後仍維持關閉。

新版主視窗開啟時，守護可能還在啟動。只有確認監聽已開始，而且執行中的程序、執行檔及組建編號都與目前的 AppPorts 相符，依賴守護的應用程式才會重新顯示「可用」。等待期間顯示「檢測中」，徽章會自動更新。若設定裡持續顯示守護尚未就緒，可到「背景代理」點選「重試」。[背景代理設定](/docs/settings)

在 macOS 15.7.7 的隔離測試中，build 80 透過應用程式內安裝流程換成事先備妥的 build 81 後，新守護自動啟動。我們用兩份保留原始簽章的 DeepSeek Harness 與一份超過 64 MiB 的日誌，重現已知的安裝失敗。新守護將外接磁碟上的 0.2.1-rc.2 更新到 0.2.2-rc.5，任務中心只出現一筆成功記錄，從原本的本機入口冷啟動也開啟了外接磁碟上的 rc.5。這項測試使用事先備妥的候選套件與失敗記錄，正式更新來源沒有發佈這次組建。

## 外接磁碟更新實測 {#examples}

2026 年 11 月 21 日，IINA 在非鎖定遷移後透過 Sparkle，從 **1.3.5 更新至 1.5.1**。結束後從原本的本機入口冷啟動，實際執行的是外接磁碟上的 1.5.1。這次由 IINA 自行完成更新。

在已關閉更新守護的 macOS 15.7.7 測試機上，Firefox 從 160.0 更新至 160.0.1，Google Chrome 從 153.0.8010.48 更新至 158.0.8127.37。結束後從原本的本機入口重新開啟，執行的都是外接磁碟上的新版，開發者簽章有效。

在隔離測試中，CC Switch 4.0.30 使用同卷暫存目錄成功更新至 4.0.38，從原入口重新開啟後，執行的是保有開發者簽章的外接磁碟新版。舊版 AppPorts 建立的標準入口會在掃描應用程式列表時自動重新整理，下次照常啟動即可生效。直接開啟外接磁碟上的應用程式或透過傳統符號連結啟動時，舊版外掛程式會使用系統預設暫存目錄。

Clash Verge 預設保留在本機。在隔離環境中將 2.5.5 放在外接磁碟後，啟動時會要求移回本機，選擇取消就會結束。

同日，DeepSeek Harness 從 **0.2.2-rc.3 更新至 rc.5** 時，ShipIt 安裝失敗並結束。日誌已累積約 64 MiB，舊守護無法讀到本次結果。複測時，獨立啟動的修正版守護從日誌末尾辨識出這次失敗，完成外接磁碟安裝，任務中心顯示已接手成功。再從原本的入口冷啟動，執行的是外接磁碟上的 rc.5。這次驗證了該次請求及快取套件的組合。其他使用 ShipIt 的應用程式能否復原，仍取決於它在當次安裝留下了哪些資料。
